Раннер (или в терминологии некоторых платформ — агент) — это процесс, который получает задания от CI/CD-сервера и выполняет их на конкретной машине. CI/CD-сервер (GitLab, GitHub Actions, Jenkins) управляет очередью заданий, а раннер — тот, кто их физически исполняет.

По месту размещения раннеры делятся на два типа:

По области видимости runners делятся на два типа:
- Shared runner доступен всем проектам в GitLab-инстансе. Его регистрирует администратор один раз, и любой проект может использовать его без дополнительной настройки. Это удобно для небольших команд, где нет смысла держать отдельный агент под каждый репозиторий.
- Specific runner привязан к конкретному проекту или группе. Его регистрируют через Settings → CI/CD → Runners в интерфейсе проекта. Такой runner используют, когда job требует особого окружения: специального железа, лицензионного ПО или изолированной сети.


Раннер постоянно опрашивает CI/CD-сервер по принципу **long polling**: «Есть ли для меня задание?». Когда pipeline запускается, сервер ставит задания в очередь и отдаёт их свободным раннерам. Раннер выполняет шаги, пишет лог и возвращает результат серверу.

Executor (исполнитель) определяет, в какой среде runner запускает job. Выбор executor-а задаётся при регистрации runner-а, а не в .gitlab-ci.yml.

- Shell — команды выполняются непосредственно на хостовой машине через командную оболочку. Такой вариант прост в настройке, но задачи могут влиять друг на друга через общую файловую систему и другие ресурсы.
- Docker — задача выполняется в отдельном контейнере, обычно создаваемом на основе указанного Docker-образа. Это обеспечивает более изолированное и воспроизводимое окружение, хотя степень изоляции зависит от конфигурации.
- Kubernetes — для выполнения каждой задачи runner обычно создаёт отдельный Pod в Kubernetes-кластере. Это упрощает масштабирование и параллельное выполнение задач.

Пример конфигурации GitLab Runner с Docker-исполнителем (файл config.toml):

```
[[runners]]
  name = "my-docker-runner"
  url = "https://gitlab.com/"
  token = "TOKEN"
  executor = "docker"
  [runners.docker]
    image = "ubuntu:22.04"
```

Здесь каждое задание будет запускаться в контейнере на базе ubuntu:22.04, а после завершения контейнер удаляется. Также в job можно указать конкретный образ через ключевое слово image, перезаписывая образ по умолчанию.

Если у вас несколько раннеров, задания выполняются параллельно — это сокращает общее время pipeline. Раннерам при регистрации можно назначать теги, а в конфигурации задания указывать, какой тег нужен:

```
build-job:
  tags:
    - linux
    - docker
```

Задание попадёт только на раннер, у которого есть оба тега linux и docker. Если ни один runner не имеет нужных тегов, job зависнет в статусе pending. Это частая причина застрявших пайплайнов.
