CI/CD pipeline — это автоматизированная последовательность шагов, которая превращает изменение в коде в работающий продукт на сервере. Классический pipeline состоит из трёх основных этапов: Build (сборка), Test (тестирование) и Deploy (развёртывание). Они выполняются строго по порядку — следующий этап запускается только если предыдущий завершился успешно.

**Build**
На этом этапе исходный код превращается в исполняемый артефакт: скомпилированный бинарник, Docker-образ, JAR-файл, собранный фронтенд. Здесь же устанавливаются зависимости. Результат этапа — артефакт, который передаётся дальше по конвейеру.

Пример для Node.js-приложения в конфигурации GitLab CI:
```
build:
  stage: build
  script:
    - npm install
    - npm run build
  artifacts:
    paths:
      - dist/
```

**Test**
Здесь запускаются автоматические проверки: юнит-тесты (unit tests), интеграционные тесты, линтеры, проверки безопасности. Цель — убедиться, что изменение не сломало существующую функциональность.

```
test:
  stage: test
  script:
    - npm run test
    - npm run lint
```

**Deploy**
Прошедший проверки артефакт доставляется на целевую среду (environment). Обычно pipeline содержит несколько окружений с разными правилами запуска:

```
deploy_staging:
  stage: deploy
  script:
    - scp -r dist/ user@staging-server:/var/www/app
  environment:
    name: staging

deploy_production:
  stage: deploy
  script:
    - scp -r dist/ user@prod-server:/var/www/app
  environment:
    name: production
  when: manual
```

Ключевое свойство всей цепочки — идемпотентность: повторное выполнение этапа при тех же входных данных должно приводить к тому же ожидаемому состоянию системы, не вызывая нежелательных побочных эффектов. CI/CD-система предоставляет механизмы автоматического и повторного (при завершении ошибкой) запуска задач, однако сама по себе не гарантирует их идемпотентность. Ответственность за её обеспечение лежит на разработчиках и инженерах, проектирующих pipeline: они должны учитывать возможность повторного выполнения при написании скриптов, выборе инструментов и проектировании каждого этапа.

![20261015110907](../resources/20261015110907.png)

В CI/CD-пайплайне исходный код, отправленный разработчиком в репозиторий, должен оставаться неизменным в процессе проверок. Задача CI — не исправлять код за разработчиком, а проверить, что разработчик отправил качественный, правильно отформатированный и рабочий код.
