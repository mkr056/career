Когда вы создаете/запускаете контейнер, Docker берёт все слои образа (они остаются read-only) и добавляет поверх них тонкий записываемый слой, который принадлежит только этому контейнеру.

Запустить 10 контейнеров из одного образа дёшево — каждый добавляет лишь небольшой writable layer, а сам образ не копируется.

Любые изменения внутри работающего контейнера — созданные файлы, логи, изменённые конфиги — попадают только в writable layer. Слои образа при этом не затрагиваются. Когда контейнер удаляется, его writable layer уничтожается вместе с ним. Всё, что туда записалось, теряется.

Когда процесс внутри контейнера пытается изменить файл из read-only слоя, Docker не трогает оригинал. Вместо этого он копирует файл в writable layer и все дальнейшие операции идут с копией. Этот механизм называется Copy-on-Write (CoW).

Когда Docker запускает контейнер из образа, он не копирует весь образ на диск заново. Вместо этого используется объединяющая файловая система (union filesystem) — механизм, позволяющий накладывать несколько директорий друг на друга так, что снаружи они выглядят как одна.

Современный Docker по умолчанию использует драйвер overlay2 — реализацию union filesystem, встроенную в ядро Linux. Он работает с двумя директориями:
- `lowerdir` — один или несколько read-only слоёв образа;
- `upperdir` — слой записи контейнера;
- `merged` — объединённое представление, которое видит процесс внутри контейнера.

Посмотреть, какой драйвер использует ваш Docker, можно командой: `docker info | grep "Storage Driver"`.

# Жизненный цикл контейнера
Контейнер проходит через несколько чётко определённых состояний.

![20261020130505](../resources/20261020130505.png)

Переходы не обязательно линейны.

# docker create (created)
Команда `docker create` создаёт новый контейнер из указанного образа (скачивая образ из реестра, если его ещё нет локально), но не запускает процесс внутри. Docker подготавливает записываемый слой поверх образа и сохраняет конфигурацию.

По умолчанию Docker присваивает контейнеру случайное имя. Флаг `--name` задаёт понятное имя, по которому удобно обращаться к контейнеру в других командах. Имя должно быть уникальным. Если контейнер с таким именем уже существует (даже остановленный), нужно сначала удалить его или выбрать другое имя.

Флаг `-it` — сочетание двух флагов: `-i` (`--interactive`, оставить stdin контейнера открытым) и `-t` (`--tty`, выделить псевдотерминал для контейнера). Эти флаги задают параметры интерактивности контейнера, позволяя в дальнейшем взаимодействовать с контейнером через терминал, например, используя `docker start -ai` или `docker attach`.

Флаг `--rm` удаляет контейнер сразу после его остановки.

По умолчанию контейнер работает в изолированной сетевой среде Docker. Чтобы сервис внутри контейнера был доступен снаружи, нужно пробросить порт (port binding). Синтаксис: `-p <порт_хоста>:<порт_контейнера>`: `docker create --name web -p 8080:80 nginx`. После запуска контейнера запрос к `http://localhost:8080` на хосте будет перенаправлен на порт `80` контейнера, где работает Nginx. Для контейнера, который слушает несколько портов, просто повторите флаг `-p`.

Если протокол не указан, Docker использует TCP. Чтобы пробросить UDP-порт, добавьте суффикс `/udp`. Есть важный нюанс: на какой именно сетевой интерфейс хоста привязывается этот порт. Разница между "доступен только мне" и "доступен всему интернету" определяется одним коротким фрагментом в команде. Флаг `-p` принимает расширенную форму: `-p [адрес_хоста:]порт_хоста:порт_контейнера`. Часть `адрес_хоста` -- это IP-адрес сетевого интерфейса (bind address), к которому привязывается проброшенный порт. Если адрес не указан, Docker по умолчанию использует `0.0.0.0`, то есть все интерфейсы.

![20261026224010](../resources/20261026224010.png)

Loopback-интерфейс -- это виртуальный сетевой интерфейс с адресом `127.0.0.1`. Трафик на нём никогда не покидает машину. Важно понимать: когда вы пишете просто `-p 8080:80` без указания адреса, Docker подставляет `0.0.0.0`. Документация Docker прямо говорит: "when a container's ports are mapped without any specific host address, the Docker daemon publishes ports to all host addresses". Это значит, что `-p 8080:80` и `-p 0.0.0.0:8080:80` -- одно и то же.

Если вы хотите, чтобы Docker по умолчанию привязывал порты только к localhost, добавьте в файл `/etc/docker/daemon.json`:

```
{
  "ip": "127.0.0.1"
}
```

После этого перезапустите демон Docker. Теперь команда `-p 8080:80` будет привязывать порт к `127.0.0.1`, а не к `0.0.0.0`. Это полезная мера безопасности на серверах, где вы не хотите случайно выставить сервис наружу.

Иногда вам не важно, какой именно порт на хосте будет занят, -- вы просто хотите быстро получить доступ ко всему, что контейнер готов отдать наружу. Для этого существует флаг `-P` (или `--publish-all`).

 Флаг `-P` берёт все порты, перечисленные через EXPOSE, и публикует каждый из них на случайный свободный порт хоста из эфемерного диапазона, обычно это порты выше 32767. Команда `docker port <имя_или_id_контейнера>` выведет все активные маппинги.

Флаг `-e` и `--env` (полная форма) (environment) передаёт переменную окружения внутрь контейнера. Флаг `-e` можно указывать несколько раз — каждый раз для одной переменной.

```
docker run -d \
  --name db \
  -e POSTGRES_USER=admin \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=myapp \
  -p 5432:5432 \
  postgres
```

Если указать имя переменной без знака `=`, Docker возьмёт её значение из вашего текущего окружения на хосте. Если переменная не задана на хосте, она просто не попадёт в контейнер — ошибки не будет.

Некоторые образы уже содержат переменные окружения, заданные инструкцией `ENV` в Dockerfile. Флаг `-e` перезаписывает их.

Docker поддерживает флаг --env-file, который загружает переменные окружения из файла. В файле одна переменная на строку в виде `КЛЮЧ=значение`. Передайте путь к файлу через флаг `--env-file`. Флаг `--env-file` можно указывать несколько раз, чтобы загрузить переменные из разных файлов. Также его можно комбинировать с флагом `-e`. Docker обрабатывает переменные в порядке их появления. Если одна и та же переменная задана и в файле, и через `-e`, приоритет получает та, что указана последней в командной строке. В отличие от shell-скриптов, Docker не интерпретирует кавычки и не раскрывает переменные вида `$HOME` внутри файла. Всё, что написано после `=`, передаётся как есть. Поэтому значения в `.env`-файле записывайте без кавычек и без ссылок на другие переменные.

# docker start (running)
Команда `docker start` запускает главный процесс контейнера, указанный при создании.

Флаг `-a` (`--attach`) позволяет видеть `STDOUT` и `STDERR` контейнера непосредственно в терминале.

Флаг `-i` позволяет передавать контейнеру команды через STDIN, обеспечивая интерактивное взаимодействие.

# docker pause (paused)
Команда `docker pause` отправляет сигнал `SIGSTOP` всем процессам контейнера. Они замирают — не потребляют CPU, но остаются в памяти и на диске. `docker unpause` возобновляет работу с той же точки.

# docker stop / docker kill (stopped  (exited))
Команда `docker stop` сначала отправляет `SIGTERM`, даёт главному процессу 10 секунд (можно изменить флагом `-t`) на корректное завершение, затем — `SIGKILL`. `docker kill` отправляет `SIGKILL` немедленно. У обеих команд можно отправить другой сигнал через флаг `-s` (`--signal`). Файловая система контейнера при этом сохраняется — данные не теряются до удаления. Как только главный процесс завершается, контейнер переходит в состояние exited. Число в скобках — это код выхода. Код `0` означает успешное завершение без ошибок, любое другое число -- ошибку.

# docker rm (removed)
Команда `docker rm` удаляет контейнер по идентификатору или имени и его writable layer. Попытка удалить работающий контейнер без флага `-f` (отправляет `SIGKILL`) завершится ошибкой. Нужно сначала остановить контейнер. Если передано несколько контейнеров, команда удалит остановленные контейнеры, а при наличии работающих выдаст ошибку, продолжив обработку остальных.

Разом убрать все остановленные контейнеры: `docker container prune`.

Можно скомбинировать `docker ps` с фильтром и с флагом `-q` и подставить результат в `docker rm`: `docker rm $(docker ps --filter status=exited -q)`. Если подходящих контейнеров нет, `docker rm` запустится без аргументов и выдаст ошибку.

По умолчанию `docker rm` не трогает тома, связанные с контейнером. Если при создании контейнера были созданы анонимные тома и они больше не нужны, добавьте флаг `-v`. Именованные тома при этом сохраняются -- удаляются только анонимные, то есть те, которые были созданы без явного имени.

# docker run
Команда `docker run` -- это сокращение для `docker create` +  `docker start`.

Флаг `-d` (сокращение от `--detach`) запускает контейнер в в фоновом режиме. Терминал не блокируется -- Docker выводит только идентификатор контейнера и возвращает управление вам. Контейнер при этом работает "за кулисами".

# docker restart
Команда `docker restart` останавливает контейнер и тут же запускает его заново. По сути это `docker stop` + `docker start` в одном вызове. Доступны только флаги `-t` и `-s` аналогично `docker stop`.

# docker wait
Команда `docker wait` блокирует терминал до тех пор, пока указанный контейнер(ы) не будет остановлен, а затем выводит его код выхода.

# docker inspect
Проверить текущее состояние контейнера в любой момент позволяет команда: `docker inspect --format '{{.State.Status}}' lifecycle-demo`.

# docker ps
По умолчанию команда `docker ps` показывает только запущенные контейнеры. Чтобы увидеть контейнеры во всех состояниях, включая остановленные, нужен флаг `--all` (или сокращённо `-a`).

Каждая строка в таблице `docker ps` содержит семь столбцов:
- CONTAINER ID: Уникальный идентификатор контейнера (укороченный до 12 символов)
- IMAGE: Образ, из которого создан контейнер
- COMMAND: Команда, запущенная внутри контейнера
- CREATED: Когда контейнер был создан
- STATUS: Текущее состояние: `Up`, `Exited (0)`, `Created` и т.д.
- PORTS: Проброшенные или открытые порты
- NAMES: Имя контейнера (заданное через `--name` или сгенерированное автоматически)

`-q` (`--quiet`) -- выводит только идентификаторы контейнеров, по одному на строку.

-f (`--filter`) -- фильтрует вывод по условию.

# docker logs
Когда контейнер работает в фоновом режиме (с флагом `-d`), вы не видите его вывод в терминале. Чтобы узнать, что происходит внутри, используется команда `docker logs <имя_или_id_контейнера>`. Она показывает всё, что контейнер записал в свои стандартные потоки вывода: stdout и stderr в том порядке, в котором записи появлялись. Если перенаправить вывод в терминале, потоки разделяются. Например, чтобы увидеть только ошибки: `docker logs timer 1>/dev/null`. Обратная ситуация -- только stdout без ошибок: `docker logs timer 2>/dev/null`.

Пока контейнер не удалён, его логи сохраняются. Это удобно для диагностики: контейнер упал, но вы всё ещё можете прочитать, что он вывел перед завершением.

Docker записывает только то, что главный процесс контейнера (PID 1) отправляет в stdout и stderr. Если приложение пишет в файл внутри контейнера (например, в `/var/log/app.log`), эти записи в `docker logs` не попадут. Именно поэтому при контейнеризации приложения принято настраивать его так, чтобы логи шли в stdout/stderr, а не в файлы. Например, официальный образ nginx делает символические ссылки из файлов логов на `/dev/stdout` и `/dev/stderr`, чтобы всё было доступно через `docker logs`.

Флаг `--tail` (короткая форма `-n`) ограничивает вывод последними N строками. Передавать отрицательные числа или нецелые значения нельзя -- Docker в таком случае сбросит значение на `all` и покажет всё.

Флаг `--follow` (короткая форма `-f`) переводит команду в режим непрерывного потока. Docker не завершает работу после вывода текущих записей, а продолжает транслировать новые строки из stdout и stderr контейнера по мере их появления. Вывод будет обновляться, пока вы не нажмёте `Ctrl+C`.

По умолчанию Docker выводит «голые» строки лога. Флаг `--timestamps` (короткая форма `-t`) добавляет к каждой строке временную метку в формате RFC 3339 с наносекундной точностью.

Ещё два полезных флага, о которых стоит знать: `--since` и `--until`. Они фильтруют лог по времени (включительно). Значение можно задавать как абсолютную дату (формат RFC 3339, пример: `2013-01-02T13:23:37Z`), так и относительный интервал (`42m`, `2h`, `1m30s`).

# docker exec
Контейнер работает в фоне, внутри него крутится процесс, но вам нужно заглянуть внутрь. Для этого существует команда `docker exec` (execute) -- она запускает новую команду внутри уже работающего контейнера, не останавливая его основной процесс. Работает только с контейнерами в статусе Running. Если контейнер остановлен или поставлен на паузу, Docker вернёт ошибку.

Контейнер указывается по имени или ID. После него идёт команда, которую нужно выполнить.

Для составных команд с `&&` или `|` оберните их в `sh -c`.

Самый частый сценарий -- открыть интерактивную сессию внутри контейнера. Для этого нужны два флага: `-i` и `-t`. - `-i` (`--interactive`) — оставляет `STDIN` открытым, чтобы можно было передавать команды внутрь контейнера. `-t` (`--tty`) — выделяет псевдотерминал (TTY), чтобы процесс работал как в обычном терминале. 

Флаг `-e` позволяет передать переменную окружения в запускаемый процесс.

Флаг `-w` задаёт рабочую директорию для команды. Это эквивалентно тому, чтобы сначала сделать `cd`.

# docker system prune
При запуске команды по умолчанию, Docker покажет предупреждение и спросит подтверждение. Если ответить `y`, будут удалены:
- контейнеры: все остановленные
- сети: не используемые ни одним контейнером
- образы: только висячие
- кэш сборки: неиспользуемые build cache

Обратите внимание: тома по умолчанию не удаляются. Это сделано специально, чтобы случайно не потерять данные базы или файлы приложения.

`--volumes` -- добавляет к очистке анонимные тома, не привязанные ни к одному контейнеру.

`-a` (`--all`) -- удаляет не только висячие образы, но и все образы, у которых нет ни одного связанного контейнера. Это значит, что скачанные, но неиспользуемые образы тоже будут удалены.

`-f` (`--force`) -- пропускает запрос подтверждения.

Флаг `--filter` позволяет ограничить очистку.

Посмотреть сколько дискового пространства занимают образы, контейнеры, тома и кэш, можно командой: `docker system df`.

Данные, которые должны пережить контейнер, нужно хранить за его пределами. Именно для этого Docker предоставляет механизм томов (volumes) -- внешних хранилищ, которые не зависят от жизненного цикла контейнера. Том продолжает существовать, даже когда контейнер, который его использовал, давно удалён.
