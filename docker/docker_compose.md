Docker Compose — инструмент для описания и запуска многоконтейнерных приложений. Вместо того чтобы запускать каждый контейнер вручную длинной командой `docker run`, вы описываете всю конфигурацию в одном файле — `docker-compose.yml`. Это YAML-файл с фиксированной структурой верхнего уровня.

Ключ version когда-то указывал версию формата Compose-файла: 2, 2.1, 3, 3.8, 3.9 и так далее. Так было устроено первое поколение файлов Compose, где формат менялся между версиями и от значения ключа зависело, какие возможности синтаксиса доступны.

`version: "3.9"`

С переходом на единую спецификацию Compose (Compose Specification), на которую опирается Docker Compose v2 и совместимые инструменты, деление на пронумерованные версии исчезло: все ключи спецификации доступны независимо от того, что написано в файле. Ключ `version` в неё не входит, и при запуске Compose v2 выводит предупреждение об устаревшем (obsolete) атрибуте. В новых проектах его не пишут вовсе. Встретить `version` вы можете в старых репозиториях — это признак файла эпохи Compose v1. При правке такого файла ключ обычно удаляют вместе с переносом на актуальный синтаксис.

Ключ services — главный раздел файла. Каждый дочерний ключ внутри него описывает один контейнер: его образ, порты, переменные окружения и зависимости. Имя сервиса становится его DNS-именем внутри сети Compose.

```
services:
  web:
    image: nginx:alpine
  db:
    image: postgres:15
```

Здесь объявлены два сервиса: `web` и `db`.

По умолчанию Compose создаёт одну общую сеть для всех сервисов файла, и они могут обращаться друг к другу по имени сервиса. Если нужна более тонкая изоляция — например, чтобы `frontend` не имел прямого доступа к `db` — сети объявляют явно.

```
networks:
  backend:
  frontend:
```

Сервисы подключаются к нужным сетям через ключ `networks` внутри описания сервиса. Сеть без дополнительных параметров создаётся с драйвером `bridge` — стандартный вариант для локальной разработки.

Ключ `volumes` на верхнем уровне объявляет именованные тома, которыми Docker управляет самостоятельно: данные хранятся вне файловой системы контейнера и переживают его перезапуск.

```
volumes:
  postgres_data:
  redis_cache:
```

Объявление тома здесь — это регистрация его имени. Чтобы том реально использовался, его нужно подключить внутри сервиса через ключ `volumes` уже на уровне сервиса. Типичная ошибка начинающих — указать том в сервисе, но забыть объявить его на верхнем уровне: Compose выдаст ошибку `service "db" refers to undefined volume`.

Каждый сервис в `docker-compose.yml` — это отдельный контейнер со своими параметрами запуска. Все эти параметры задаются в виде ключей под именем сервиса.

Ключ `image` указывает готовый образ (image) из реестра. Compose скачает его при первом запуске:

```
services:
  db:
    image: postgres:15
```

Ключ `build` говорит Compose собрать образ из Dockerfile в указанной директории. 

```
services:
  api:
    build: ./api
```

Можно уточнить путь к `Dockerfile` явно через вложенный ключ `context` и `dockerfile`, но для большинства случаев достаточно указать директорию строкой. `image` и `build` можно комбинировать — тогда собранный образ получит имя из `image`.

Ключ `ports` пробрасывает порт (port mapping) из контейнера на хост-машину. Формат: `"хост:контейнер"`.

```
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
```

После этого `http://localhost:8080` будет отвечать из контейнера на порту 80.

Ключ `environment` передаёт переменные окружения (environment variables) внутрь контейнера. Это стандартный способ конфигурировать приложения без изменения образа:

```
services:
  db:
    image: postgres:15
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
```

Значения можно задавать как `КЛЮЧ: значение` (словарь) или как список строк `КЛЮЧ=значение` — оба формата корректны. Хранить пароли прямо в `docker-compose.yml` допустимо только для локальной разработки; для продакшена используют `.env`-файлы и секреты.

Ключ `depends_on` указывает, какие сервисы должны быть запущены раньше текущего:

```
services:
  api:
    build: ./api
    depends_on:
      - db
  db:
    image: postgres:15
```

Здесь `api` не стартует, пока контейнер `db` не перейдёт в состояние running. Важный нюанс: `depends_on` контролирует только **порядок запуска контейнеров**, но не ждёт готовности приложения внутри. PostgreSQL может ещё инициализироваться, когда `api` уже пытается подключиться. Для ожидания реальной готовности сервиса используют скрипты типа `wait-for-it` или расширенную форму `depends_on` с условием `condition: service_healthy` — это требует настроенного `healthcheck` у зависимого сервиса.

Когда файл `docker-compose.yml` описывает несколько сервисов, нужен инструмент, который запускает, останавливает и наблюдает за всем стеком одной командой.

Команда `up` запускает все сервисы, описанные в `docker-compose.yml`. Если образов нет локально — они скачиваются; если описан `build` — образ собирается.

По умолчанию команда занимает терминал и выводит логи всех сервисов вперемешку. Для фонового запуска используют флаг `-d`.

Флаг `--build` принудительно пересобирает образы перед запуском, даже если они уже существуют.

Команда `down` останавливает и удаляет контейнеры, сети, созданные Compose. Данные в именованных томах (volumes) по умолчанию сохраняются.

Команда `stop` только останавливает контейнеры, не удаляя их. После `down` контейнеры исчезают, а сеть Compose разбирается. Флаг `-v` дополнительно удаляет именованные тома.

Команда `ps` показывает состояние контейнеров текущего стека: имя, команду, статус и проброшенные порты.

Команда `logs` выводит стандартный поток вывода контейнеров. Без аргументов — логи всех сервисов.

Флаг `-f` (follow) переключает в режим реального времени.

Чтобы смотреть логи конкретного сервиса, укажите его имя из `docker-compose.yml`.

Флаг `--tail` ограничивает количество последних строк: `docker compose logs --tail=50 db`.

Хранить пароли, имена баз данных и API-ключи прямо в `docker-compose.yml` — плохая практика: файл попадает в репозиторий, и секреты становятся видны всем. Решение — вынести значения в отдельный файл переменных окружения (`.env file`) и ссылаться на них через подстановку.

Docker Compose автоматически читает файл `.env` из той же директории, где лежит `docker-compose.yml`. Формат простой: одна переменная на строку.

Строки, начинающиеся с `#`, считаются комментариями. Пробелы вокруг `=` не допускаются — `KEY = value` не сработает, только `KEY=value`.

После того как `.env` прочитан, Compose подставляет значения везде, где встречается синтаксис `${VARIABLE}` или `$VARIABLE`. Первый вариант предпочтительнее: он явный и не конфликтует с другими символами.

Если переменная не задана в `.env` и не экспортирована в окружение хоста, Compose подставит пустую строку — контейнер может запуститься с неожиданным поведением. Чтобы этого избежать, используйте синтаксис значения по умолчанию: `image: postgres:${PG_VERSION:-15}`. Здесь `:-15` означает: «если `PG_VERSION` не задана или пуста — использовать `15`». Это страховка от случайного запуска без `.env`.

Помимо подстановки в YAML, переменные можно передать прямо внутрь контейнера через ключ `env_file`. Тогда содержимое файла становится окружением процесса внутри контейнера, а не только значениями для самого YAML.

```
services:
  app:
    image: myapp:latest
    env_file:
      - .env
      - .env.production
```

Разница важная: `${VAR}` в YAML — это подстановка на уровне Compose при разборе файла. `env_file` — это передача переменных в сам контейнер во время запуска. Оба механизма можно использовать одновременно.

Полезная мелочь: в `environment:` можно указать переменную БЕЗ значения (просто `- MY_VAR`) — тогда Compose пробросит её текущее значение из окружения хоста в контейнер.

# Docker networking
Когда Docker запускает контейнер, он подключает его к виртуальной сети через один из встроенных сетевых драйверов (network drivers). Драйвер определяет, как контейнер видит другие контейнеры, хост-машину и внешний мир.

Bridge-сеть — изолированная виртуальная сеть внутри хоста. Docker создаёт виртуальный коммутатор `docker0`, и каждый контейнер получает собственный IP-адрес в этой подсети. Контейнеры одной bridge-сети могут общаться между собой, а наружу трафик идёт через NAT.

Существует два вида bridge-сетей: дефолтная (`bridge`) и пользовательская (созданная командой `docker network create`).

Пример: запустить два контейнера в одной пользовательской сети:

```
docker network create my-net
docker run -d --name app --network my-net nginx
docker run -d --name db  --network my-net postgres
```

Контейнер `app` сможет обратиться к `db` по имени `db` — без указания IP.

Host-сеть убирает сетевую изоляцию: контейнер использует сетевой стек хоста напрямую. Если приложение слушает порт 8080, он сразу доступен на хосте — без публикации через `-p`.

`docker run --network host nginx`

Это даёт минимальную задержку и упрощает конфигурацию, но контейнер видит все интерфейсы хоста. Режим работает только на Linux; на macOS и Windows Docker Desktop эмулирует его с ограничениями.

None-сеть полностью отключает сетевой стек. Контейнер не имеет ни IP-адреса, ни интерфейсов, кроме loopback. Используется для изолированных задач обработки данных, где сетевой доступ не нужен и нежелателен с точки зрения безопасности.

```
docker run --network none alpine ping 8.8.8.8
# PING 8.8.8.8: Network unreachable
```

Overlay-сеть (overlay network) создаёт виртуальную сеть поверх нескольких физических хостов. Контейнеры на разных машинах видят друг друга так, будто находятся в одной локальной сети. Это основной драйвер для Docker Swarm и мультихостовых сценариев.

Overlay требует инициализации кластера:

```
docker swarm init
docker network create --driver overlay my-overlay
```

Без активного Swarm или внешнего key-value хранилища overlay-сеть создать не получится — Docker вернёт ошибку.

Когда несколько контейнеров работают в одной пользовательской bridge-сети, им нужно находить друг друга по сети. Жёстко прописывать IP-адреса нельзя: Docker назначает их динамически, и после перезапуска контейнера адрес может измениться. Именно здесь в игру вступает DNS-резолвинг — механизм, который позволяет обращаться к контейнеру по имени, а не по адресу.

В пользовательских bridge-сетях Docker запускает собственный встроенный DNS-сервер, доступный по адресу 127.0.0.11. Каждый контейнер в такой сети автоматически настроен использовать этот сервер для разрешения имён.

Принцип работы прост: когда контейнер `app` обращается к имени `db`, запрос уходит на `127.0.0.11`, тот смотрит в свою таблицу и возвращает IP-адрес контейнера с именем `db` в той же сети.

Важно: это работает только в пользовательских сетях. В сети `bridge` по умолчанию встроенный DNS не работает, и контейнеры не находят друг друга по именам.

Docker регистрирует контейнер в DNS по двум идентификаторам:
- Имя контейнера: флаг `--name` при запуске
- Сетевой псевдоним: флаг `--network-alias`

Если имя не задано явно, Docker генерирует случайное — вроде `tender_hopper`.

Иногда нужно, чтобы несколько контейнеров отвечали на одно имя — например, два инстанса одного сервиса. Для этого используют `--network-alias`:

```
docker run -d --network my-net --network-alias backend app-image:v1
docker run -d --network my-net --network-alias backend app-image:v2
```

Теперь DNS будет возвращать оба IP-адреса при запросе имени `backend`, а клиент сам выберет, к какому подключиться. Это базовый механизм балансировки нагрузки на уровне DNS внутри Docker-сети.

В Docker Compose имена сервисов автоматически становятся DNS-именами в общей сети — поэтому сервис `web` может обращаться к `db:5432` без какой-либо дополнительной настройки.

# Volumes
По умолчанию данные внутри контейнера живут ровно столько, сколько живёт сам контейнер. Удалил контейнер — потерял данные. Чтобы данные пережили контейнер или были доступны нескольким контейнерам одновременно, Docker предлагает три механизма хранения: тома (volumes), монтирование директорий хоста (bind mounts) и временное хранилище в памяти (tmpfs).

Volume — это управляемое Docker хранилище, физически расположенное в директории `/var/lib/docker/volumes/` на хосте. Docker сам создаёт, отслеживает и изолирует это пространство от остальной файловой системы.

`docker run -v mydata:/app/data nginx`

Здесь `mydata` — имя тома, `/app/data` — путь внутри контейнера. Если том с таким именем не существует, Docker создаст его автоматически.

Volumes — рекомендуемый способ хранения для большинства сценариев: базы данных, файлы приложения, артефакты сборки. Они переносимы между машинами, поддерживают резервное копирование через `docker volume` и не зависят от структуры файловой системы хоста.

Bind mount монтирует конкретную директорию или файл с хоста прямо в контейнер. Путь задаётся абсолютно.

`docker run -v /home/user/config:/etc/app/config:ro nginx`

Флаг `:ro` делает монтирование доступным только для чтения. Контейнер видит реальные файлы хоста — любое изменение внутри контейнера немедленно отражается снаружи, и наоборот.

Bind mounts удобны для разработки: монтируете исходный код проекта в контейнер и видите изменения без пересборки образа. Но у них есть ограничение — они жёстко привязаны к структуре файловой системы конкретной машины, что усложняет переносимость.

tmpfs хранит данные исключительно в оперативной памяти хоста. При остановке контейнера данные исчезают безвозвратно.

`docker run --tmpfs /app/cache:size=100m nginx`

Этот тип подходит для временных данных, которые не должны попасть на диск: сессионные токены, промежуточные вычисления, кэш с чувствительной информацией. Скорость чтения/записи значительно выше, чем у дискового хранилища.

Важный нюанс: если при запуске контейнера указать bind mount на несуществующую директорию хоста, Docker создаст её автоматически — но с правами root. Это частая причина проблем с правами доступа, особенно когда приложение внутри контейнера работает от непривилегированного пользователя.

Когда Docker создаёт именованный том автоматически — например, через `docker run -v mydata:/app/data` — он берёт на себя все решения: где хранить данные, какие права выставить, как назвать директорию на хосте. Но в продакшене часто нужен явный контроль над жизненным циклом томов. Для этого существуют команды `docker volume create`, `docker volume inspect` и `docker volume prune`.

`docker volume create myvolume`: команда создаёт именованный том с драйвером local по умолчанию. Том появляется в системе Docker немедленно, ещё до запуска любого контейнера — это принципиальное отличие от автосоздания при docker run.

Можно задать дополнительные параметры:

```
docker volume create \
  --driver local \
  --opt type=none \
  --opt device=/srv/pgdata \
  --opt o=bind \
  pgdata
```

Здесь `--opt` передаёт параметры монтирования: тип `none` с опцией `bind` означает, что том будет указывать на конкретную директорию хоста `/srv/pgdata`. Это полезно, когда нужно точно контролировать расположение данных.

`docker volume inspect myvolume`: просмотр деталей. Вывод — JSON с полной информацией о томе. Ключевое поле — `Mountpoint`: это реальный путь на хосте, где Docker хранит данные тома. Зная его, можно напрямую скопировать данные или сделать резервную копию средствами ОС.

Чтобы получить только путь без лишнего JSON, используют шаблон `--format`: `docker volume inspect --format '{{ .Mountpoint }}' myvolume`.

Просмотр всех томов: `docker volume ls`. Осиротевший том (dangling volume) — том, который не подключён ни к одному контейнеру. Они накапливаются после `docker rm` контейнеров и занимают место на диске.

Удалить все неиспользуемые тома одной командой: `docker volume prune`. Docker запросит подтверждение и покажет, сколько места освободилось. Если нужно удалить без интерактивного запроса — флаг `-f`.

Удалить конкретный том: `docker volume rm myvolume`. Если том подключён к работающему или остановленному контейнеру, Docker откажет с ошибкой `volume is in use`. Сначала нужно удалить контейнер.

Разработчики часто удаляют контейнер командой `docker rm`, рассчитывая, что данные исчезнут вместе с ним. Но именованный том остаётся. Это защита от случайной потери данных — но и источник «мусора», если не следить за томами регулярно.
