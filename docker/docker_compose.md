Docker Compose — инструмент для описания и запуска многоконтейнерных приложений. Вместо того чтобы запускать каждый контейнер вручную длинной командой, вы описываете всю конфигурацию в одном файле — `docker-compose.yml`.

Раньше Compose устанавливался отдельно как `docker-compose` (через дефис). Современные версии Docker Desktop и Docker Engine включают Compose как плагин, и команда пишется через пробел: `docker compose`. Обе формы работают, но `docker compose` — актуальный вариант.

# version
Ключ `version` когда-то указывал версию формата Compose-файла: 2, 2.1, 3, 3.8, 3.9 и так далее. Так было устроено первое поколение файлов Compose, где формат менялся между версиями и от значения ключа зависело, какие возможности синтаксиса доступны. С переходом на единую спецификацию Compose, на которую опирается Docker Compose v2 и совместимые инструменты, деление на пронумерованные версии исчезло: все ключи спецификации доступны независимо от того, что написано в файле. Ключ `version` в неё не входит, и при запуске Compose v2 выводит предупреждение об устаревшем (obsolete) атрибуте. При использовании Docker Compose v1 поведение зависит от версии программы: до версии 1.27.0 отсутствие ключа `version` приводит к интерпретации файла в формате версии 1. Начиная с версии 1.27.0 поддерживается единая Compose Specification, позволяющая использовать современный формат файла без ключа `version`.

Вместо `version` в современных файлах используют ключ `name` -- он задаёт имя проекта. Если `name` не указан, Compose берёт имя из названия папки, в которой лежит файл.

# services
Ключ `services` — главный и обязательный раздел файла. Каждый дочерний ключ внутри него описывает один контейнер.

```
services:
  web:
    image: nginx:alpine
  db:
    image: postgres:15
```

Здесь объявлены два сервиса: `web` и `db`.

==Ключ `volumes` на верхнем уровне объявляет именованные тома, которыми Docker управляет самостоятельно: данные хранятся вне файловой системы контейнера и переживают его перезапуск.==

```
volumes:
  postgres_data:
  redis_cache:
```

==Объявление тома здесь — это регистрация его имени. Чтобы том реально использовался, его нужно подключить внутри сервиса через ключ `volumes` уже на уровне сервиса. Типичная ошибка начинающих — указать том в сервисе, но забыть объявить его на верхнем уровне: Compose выдаст ошибку `service "db" refers to undefined volume`. Двоеточие и пустое значение означает настройки по умолчанию.==

# networks
По умолчанию, каждый раз, когда вы выполняете `docker compose up`, Compose делает три вещи:
1. Создаёт сеть по умолчанию (default network) с именем `<имя_проекта>_default`.
2. Запускает контейнеры для каждого сервиса.
3. Подключает каждый контейнер к этой сети.

Ключ `networks` в файле `docker-compose.yml` позволяет создавать собственные сети и точно контролировать, какие сервисы могут общаться друг с другом.

Каждый сервис автоматически получает DNS-имя, совпадающее с его именем в файле `docker-compose.yml`. Docker запускает внутренний DNS-сервер в каждой пользовательской сети (включая ту, что Compose создаёт по умолчанию). Этот сервер знает имена всех контейнеров в сети. Когда контейнер `web` пытается обратиться к `db`, происходит следующее:
1. Контейнер `web` спрашивает встроенный DNS: "Какой IP у `db`?"
2. DNS-сервер возвращает текущий IP-адрес контейнера `db`.
3. `web` устанавливает соединение по полученному адресу.

В Compose-файле `networks` встречается в двух местах:
![20261027202909](../resources/20261027202909.png)

Оба уровня работают в паре: сначала вы объявляете сети наверху, затем подключаете к ним нужные сервисы.

```
networks:
  backend:
  frontend:
```

Пользовательские сети без дополнительных параметров создаются с драйвером `bridge`.

Compose по умолчанию формирует имя сети по шаблону `<имя_проекта>_<имя_сети>`. Если проект лежит в папке `myapp`, сеть `backend` из примера выше получит имя `myapp_backend`. Чтобы задать произвольное имя, используйте ключ `name`:

```
networks:
  backend:
    name: my_custom_backend
```

Иногда сеть создана заранее командой `docker network create`. Чтобы Compose не пытался создать её заново, а подключился к существующей, добавьте `external: true`:

```
networks:
  shared:
    name: my-pre-existing-network
    external: true
```

Если сеть с таким именем не найдена на момент запуска, Compose завершится с ошибкой "Network not found".

Когда вы запускаете проект с пользовательскими сетями, Compose выполняет три действия: создаёт все сети, перечисленные в верхнеуровневом `networks` (кроме `external`), запускает контейнеры и подключает каждый контейнер к тем сетям, которые указаны в его сервисном `networks`. Сеть по умолчанию при этом не создаётся, если хотя бы один сервис явно указал свои сети. Контейнер, у которого `networks` не задан, попадёт в сеть `default`, которую Compose создаст автоматически, если она нужна хотя бы одному сервису.

Каждый сервис в `docker-compose.yml` — это отдельный контейнер со своими параметрами запуска. Все эти параметры задаются в виде ключей под именем сервиса.

# image / build
Ключ `image` указывает готовый образ из реестра или локальный:

```
services:
  db:
    image: postgres:15
```

Ключ `build` говорит Compose собрать образ из Dockerfile в указанной директории. 

```
services:
  api:
    build: ./api
```

Можно уточнить путь к `Dockerfile` явно через вложенный ключ `context` и `dockerfile`, но для большинства случаев достаточно указать директорию строкой. `image` и `build` можно комбинировать — тогда собранный образ получит имя из `image`.

# ports
Ключ `ports` пробрасывает порт (port mapping) из контейнера на хост-машину. Формат: `"хост:контейнер"`. Если указать только контейнерный порт, Docker сам назначит свободный порт на хосте.

```
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
```

# environment
Ключ `environment` передаёт переменные окружения внутрь контейнера.

```
services:
  db:
    image: postgres:15
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
```

Значения можно задавать как `КЛЮЧ: значение` (словарь) или как список строк `КЛЮЧ=значение` — оба формата корректны. Хранить пароли прямо в `docker-compose.yml` допустимо только для локальной разработки; для продакшена используют `.env`-файлы и секреты.

# depends_on
Ключ `depends_on` указывает, какие сервисы должны быть запущены раньше текущего:

```
services:
  api:
    build: ./api
    depends_on:
      - db
  db:
    image: postgres:15
```

Здесь `api` не стартует, пока контейнер `db` не перейдёт в состояние running. Важный нюанс: `depends_on` контролирует только порядок запуска контейнеров, но не ждёт готовности приложения внутри. PostgreSQL может ещё инициализироваться, когда `api` уже пытается подключиться. Для ожидания реальной готовности сервиса используют скрипты типа `wait-for-it` или расширенную форму `depends_on` с условием `condition: service_healthy` — это требует настроенного `healthcheck` у зависимого сервиса.

# links
Иногда нужно, чтобы сервис в сети был доступен под альтернативным именем. Для этого существует ключ links:

```
services:
  web:
    build: .
    links:
      - "db:database"
  db:
    image: postgres:latest
```

Теперь из контейнера `web` база доступна и как `db`, и как `database`. При этом основное DNS-имя `db` продолжает работать для всех остальных сервисов в сети.

# docker compose up
Команда `docker compose up` запускает все сервисы, описанные в `docker-compose.yml` в текущей директории. Необязательно поднимать всё сразу. Можно указать имена нужных сервисов. Однако если у сервиса есть зависимости, объявленные через `depends_on`, они тоже будут запущены. Чтобы этого избежать, добавьте флаг `--no-deps`

По умолчанию команда занимает терминал и выводит логи всех сервисов вперемешку. Для фонового запуска используют флаг `-d`.

Если вы изменили `docker-compose.yml` (например, добавили переменную окружения или поменяли образ) и снова выполнили `docker compose up`, Compose сравнит текущую конфигурацию с уже запущенными контейнерами. Контейнеры, чья конфигурация изменилась, будут остановлены, удалены и пересозданы. Контейнеры без изменений останутся работать как есть.

Compose автоматически присваивает проекту имя, совпадающее с именем папки, в которой лежит файл. Это имя используется как префикс для контейнеров, сетей и томов. Если папка называется `myapp`, контейнеры получат имена вроде `myapp-web-1`, `myapp-db-1`. Можно переопределить имя проекта при необходимости.

Флаг `--build` принудительно пересобирает образы перед запуском, даже если они уже существуют (те, у которых указан build).

Compose умеет определять, изменилась ли конфигурация сервиса (порты, переменные окружения, тома и т.д.) с момента последнего запуска. Если изменений нет, он переиспользует существующий контейнер. Флаг `--force-recreate` отключает эту оптимизацию: Compose остановит и удалит старые контейнеры, а затем создаст новые — даже если конфигурация не менялась.

Обратите внимание на противоположный флаг `--no-recreate`: он запрещает пересоздавать контейнеры, даже если конфигурация изменилась. Использовать `--force-recreate` и `--no-recreate` одновременно нельзя — Compose выдаст ошибку, потому что они противоречат друг другу.


# docker compose down
Команда `docker compose down` останавливает и удаляет контейнеры и сети, созданные Compose для текущего проекта. Данные в томах по умолчанию сохраняются. Если нужно удалить и тома, добавьте флаг `--volumes`. Сети и тома, помеченные как `external`, не удаляются никогда — Compose считает, что ими управляет кто-то другой.

![20261027170703](../resources/20261027170703.png)

Команда `down` принимает имена сервисов. Если указать конкретный сервис, будут остановлены и удалены только его контейнеры (и зависимые от него сервисы). Сеть при этом удаляется только тогда, когда больше не остаётся ни одного работающего контейнера проекта.

По умолчанию `down` не трогает анонимные тома, но и при следующем `up` они не подключатся заново, потому что у них нет стабильного имени. Флаг `--volumes` удаляет и их тоже, помогая не копить мусор на диске.


# docker compose stop
Команда `docker compose stop` только останавливает контейнеры, не удаляя их. После `stop` можно сделать `docker compose start` и продолжить работу с теми же контейнерами.

# docker compose ps
Команда `docker compose ps` показывает состояние контейнеров текущего проекта: имя, команду, статус и проброшенные порты. По умолчанию отображаются только работающие контейнеры. Чтобы увидеть и остановленные, добавьте флаг `--all`. Можно отфильтровать контейнеры по статусу.

# docker compose logs
Команда `docker compose logs` выводит стандартный поток вывода контейнеров. Без аргументов — логи всех сервисов.

![20261027171200](../resources/20261027171200.png)

Чтобы смотреть логи конкретного сервиса, укажите его имя из `docker-compose.yml`.

Флаг `--tail` ограничивает количество последних строк: `docker compose logs --tail=50 db`.

# docker compose exec
Команда `docker compose exec` запускает произвольную команду внутри уже работающего контейнера сервиса. Это аналог `docker exec`, но вместо имени контейнера вы указываете имя сервиса из `docker-compose.yml`. По умолчанию Compose выделяет интерактивный терминал (TTY), поэтому вы сразу получите интерактивную сессию. Флаг `-T` (или `--no-tty`) убирает выделение псевдотерминала, что позволяет корректно перенаправить вывод в файл.

# env
Хранить пароли, имена баз данных и API-ключи прямо в `docker-compose.yml` — плохая практика: файл попадает в репозиторий, и секреты становятся видны всем. Решение — вынести значения в отдельный файл переменных окружения (`.env file`) и ссылаться на них через подстановку.

Docker Compose автоматически читает файл `.env` из той же директории, где лежит `docker-compose.yml`. Формат простой: одна переменная на строку.

Строки, начинающиеся с `#`, считаются комментариями. Пробелы вокруг `=` не допускаются — `KEY = value` не сработает, только `KEY=value`.

После того как `.env` прочитан, Compose подставляет значения везде, где встречается синтаксис `${VARIABLE}` или `$VARIABLE`. Первый вариант предпочтительнее: он явный и не конфликтует с другими символами.

Если переменная не задана в `.env` и не экспортирована в окружение хоста, Compose подставит пустую строку — контейнер может запуститься с неожиданным поведением. Чтобы этого избежать, используйте синтаксис значения по умолчанию: `image: postgres:${PG_VERSION:-15}`. Здесь `:-15` означает: «если `PG_VERSION` не задана или пуста — использовать `15`». Это страховка от случайного запуска без `.env`.

Помимо подстановки в YAML, переменные можно передать прямо внутрь контейнера через ключ `env_file`. Тогда содержимое файла становится окружением процесса внутри контейнера, а не только значениями для самого YAML.

```
services:
  app:
    image: myapp:latest
    env_file:
      - .env
      - .env.production
```

Разница важная: `${VAR}` в YAML — это подстановка на уровне Compose при разборе файла. `env_file` — это передача переменных в сам контейнер во время запуска. Оба механизма можно использовать одновременно.
