Dockerfile — это текстовый сценарий, по которому Docker собирает образ. Каждая строка в нём содержит инструкцию и её аргументы. Каждая инструкция создаёт промежуточный результат, который становится основой для следующей.

# docker build
Базовая форма команды выглядит так: `docker build [ОПЦИИ] ПУТЬ`. `ПУТЬ` -- это обязательный аргумент. Минимальная рабочая команда: `docker build .` соберёт образ из Dockerfile, но не присвоит ему читаемое имя -- только длинный идентификатор.

Флаг `-t` (полная форма `--tag`) задаёт имя образа в формате `имя:тег`. Тег обычно обозначает версию. Если тег не указать, Docker автоматически подставит `latest`. Можно указать `-t` несколько раз, чтобы присвоить образу сразу два имени. Имя образа может включать путь к реестру, например `myregistry.io/team/myapp:v1`, но на начальном этапе достаточно простых имён.

По умолчанию Docker ищет файл с именем `Dockerfile` в корне контекста сборки. Контекст сборки — это набор файлов и директорий, которые Docker передаёт сборщику при сборке образа. Вы задаёте его последним аргументом команды `docker build`. Инструкции в Dockerfile могут обращаться только к файлам внутри контекста (иначе ошибка).

Если файл называется иначе или лежит не в корне контекста сборки, используйте флаг `-f`: `docker build -f docker/build.Dockerfile .`. Здесь Docker возьмёт инструкции из файла `docker/build.Dockerfile`, а контекстом сборки останется текущая директория (`.`). Это полезно, когда в проекте несколько Dockerfile для разных целей. Файл может лежать и вне контекста. Флаг `--no-cache` заставляет Docker выполнить каждую инструкцию заново. В выводе вы не увидите ни одной пометки `CACHED` — все шаги пройдут с нуля.

# .dockerignore
Файл `.dockerignore` работает как `.gitignore`: он перечисляет файлы и папки, которые нужно исключить из контекста сборки. Docker ищет его в корне контекста.

Если в проекте несколько Dockerfile, каждому можно назначить свой файл исключений. Для этого добавьте `.dockerignore` к имени Dockerfile:

# Чтение вывода сборки
Каждая инструкция Dockerfile (FROM, COPY, RUN и т.д.) превращается в отдельный шаг сборки. Docker нумерует их в формате `Step X/N`, где N -- общее количество инструкций.

После каждого шага появляется строка вида `---> a1b2c3d4e5f6`. Это идентификатор слоя -- уникальный хэш промежуточного образа, который Docker создал на этом шаге. Строка `Running in ...` означает, что Docker запустил временный контейнер для выполнения команды (например, RUN).

Пометка Using cache (или CACHED в новом формате вывода BuildKit) означает, что Docker не выполнял этот шаг заново, а взял готовый слой из кэша.

Самое важное -- две последние строки:
- Successfully built f6a7b8c9d0e1 -- финальный ID образа. Это хэш готового образа. По нему можно создать контейнер.
- Successfully tagged myapp:latest -- подтверждение, что образу присвоен тег, указанный через флаг `-t`.

# FROM
FROM — обязательная первая инструкция (исключение ARG, объявляющие переменные сборки). Она задаёт базовый образ, поверх которого строится всё остальное: `FROM ubuntu:22.04`. Если написать имя образа с опечаткой или указать несуществующий тег, Docker выдаст ошибку. Хорошая практика — указывать конкретный тег версии, а не `latest`. Образ с тегом `latest` может обновиться в любой момент и сломать воспроизводимость сборки.

# WORKDIR
WORKDIR задаёт рабочую директорию для всех последующих инструкций. Если указанная директория не существует, Docker создаст её автоматически.

# EXPOSE
Инструкция EXPOSE объявляет, на каких портах приложение внутри контейнера принимает соединения. Сама по себе инструкция EXPOSE ничего не пробрасывает -- она лишь документирует намерение.

# RUN
RUN выполняет команду внутри образа во время сборки.

```
RUN apt-get update && apt-get install -y curl \
    && rm -rf /var/lib/apt/lists/*
```

# COPY, ADD
Обе инструкции копируют файлы с хост-машины в образ, но ведут себя по-разному.
- COPY: Копирует файлы и директории из контекста сборки
- ADD: То же, плюс распаковывает `.tar`-архивы и загружает файлы по URL

```
COPY requirements.txt /app/requirements.txt
COPY . /app
```

Источник -- путь относительно корня контекста. Назначение -- абсолютный или относительный путь внутри образа. Если назначение относительное, оно отсчитывается от текущей рабочей директории (задаётся через WORKDIR). Если директория в назначеении не существует, Docker создаст её автоматически. Можно указать несколько источников. В этом случае назначение должно быть директорией и заканчиваться на `/`. Если источник -- директория, копируется её содержимое (но не сама папка). ## Завершающий слэш имеет значение. Если вы хотите положить файл в директорию, всегда ставьте `/` в конце пути назначения.

![20261027123021](../resources/20261027123021.png)

Рекомендация — использовать `COPY` по умолчанию. `ADD` применяют только тогда, когда нужна автоматическая распаковка архива. Скрытое поведение `ADD` с URL и архивами делает Dockerfile менее предсказуемым.


# ENTRYPOINT, CMD
Обе инструкции определяют, что запускается при старте контейнера, но роли у них разные.

ENTRYPOINT задаёт исполняемый файл контейнера — основной процесс контейнера. Он не перезаписывается при передаче аргументов в `docker create`. Переопределить его можно только флагом `--entrypoint`.

CMD задаёт аргументы по умолчанию. Если при запуске контейнера передать другие аргументы, `CMD` будет проигнорирован целиком. В Dockerfile допустима только одна действующая инструкция CMD. Если вы напишете несколько CMD подряд, сработает только последняя. Остальные будут проигнорированы без ошибки -- Docker не предупредит вас об этом.

```
ENTRYPOINT ["python", "app.py"]
CMD ["--port", "8080"]
```

`docker create myimage --port 9090` контейнер при запуске выполнит `python app.py --port 9090` — `CMD` заменился переданным аргументом, а `ENTRYPOINT` остался.

Если в Dockerfile только `CMD` без `ENTRYPOINT`: `CMD ["python", "app.py"]`.

Обе инструкции поддерживают две формы записи. Exec-форма — массив JSON (`["python", "app.py"]`) запускает процесс напрямую и является предпочтительной. 

Shell-форма — строка без скобок: (`python app.py`). Docker неявно оборачивает команду в `/bin/sh -c "..."`. Это означает, что реальным процессом с PID 1 становится `/bin/sh`, а не ваше приложение. Следствие: сигнал `SIGTERM`, который Docker посылает при `docker stop`, получает оболочка, а не процесс приложения — контейнер не завершается корректно и Docker принудительно убивает его через 10 секунд.

Если написать ENTRYPOINT в shell-форме, любые CMD и аргументы `docker run` будут проигнорированы.

Важные правила exec-формы:
- Элементы оборачиваются только в двойные кавычки ("). Одинарные кавычки (') приведут к ошибке.
- Каждый аргумент -- отдельный элемент массива.
- Смешивание форм: если `ENTRYPOINT` указан в exec-форме, а `CMD` — в shell-форме, они не объединяются как ожидается. Shell-форма `CMD` преобразуется в `/bin/sh -c "..."` и передаётся как один аргумент в `ENTRYPOINT`.

Если в вашем Dockerfile нет CMD (и нет ENTRYPOINT), контейнер унаследует CMD от базового образа. Например, у образа `ubuntu` по умолчанию CMD -- это `bash`. Если же ни в вашем Dockerfile, ни в базовом образе CMD не задана, контейнер не сможет запуститься без явного указания команды в `docker create`.

Правило для запоминания: если образ — это инструмент с фиксированной точкой входа, используйте `ENTRYPOINT` в exec-форме и `CMD` для аргументов по умолчанию; если образ универсальный и команда должна легко меняться — достаточно `CMD` в exec-форме.

# Слои
Образ (image) — это неизменяемый шаблон, из которого создаются контейнеры. Docker-образ состоит из слоёв, наложенных друг на друга. Каждая инструкция в Dockerfile, которая изменяет файловую систему создаёт отдельный слой — неизменяемый снимок файловой системы или набор изменений (дельта) относительно предыдущего слоя. Docker хранит эти слои и при повторной сборке проверяет, изменилась ли инструкция или затронутые ею файлы. Если нет — слой берётся из кэша (build cache) без повторного выполнения. Это ключевой механизм, который определяет скорость пересборки.

Слои хранятся на диске один раз. Если два образа используют одинаковый слой, Docker не дублирует его — оба образа ссылаются на одни и те же данные.

Посмотреть слои конкретного образа можно командой: `docker image inspect nginx --format '{{json .RootFS.Layers}}'`. Вы увидите список SHA256-хешей — каждый хеш соответствует одному слою на диске.

Не все инструкции добавляют слой с файлами. Реальные слои создают инструкции, меняющие содержимое файловой системы. Инструкции вроде `CMD`, `ENV`, `EXPOSE`, `WORKDIR` записывают только метаданные образа. Они технически тоже создают промежуточные шаги сборки, но не добавляют данных в файловую систему.

Docker проверяет кэш последовательно, сверху вниз. Как только одна инструкция признаётся «изменившейся», все последующие инструкции тоже выполняются заново — даже если они сами не менялись. Это называется инвалидацией кэша. Для инструкций `RUN` Docker сравнивает текст команды. Для `COPY` и `ADD` — контрольные суммы копируемых файлов. Достаточно изменить один файл в директории, и весь слой `COPY` пересчитывается. Именно поэтому `.dockerignore` напрямую влияет на эффективность кэширования: файлы, исключённые из контекста, не участвуют в проверке.

Практическое следствие из описанного выше: размещай инструкции в порядке возрастания частоты изменений. То, что меняется редко, — в начало. То, что меняется часто, — в конец.

Каждый `RUN` создаёт отдельный слой. Несколько команд объединяют через `&&` в одну инструкцию `RUN`. Например, очистка кэша пакетного менеджера в той же строке обязательна: если вынести `rm` в отдельный `RUN`, кэш уже будет зафиксирован в предыдущем слое, увеличивая размер образа.

Команда `docker history` показывает слои готового образа.

# Multi-stage build
Классическая проблема: чтобы скомпилировать Go-приложение, нужен компилятор весом ~300 МБ. Но для запуска скомпилированного бинарника компилятор не нужен совсем. Без multi-stage build образ тащит за собой весь инструментарий сборки — компиляторы, пакетные менеджеры, заголовочные файлы. Итоговый образ раздувается до сотен мегабайт лишнего веса.

Multi-stage build позволяет описать несколько этапов в одном Dockerfile, а в финальный образ скопировать только нужные артефакты.

Ключевые элементы:
- `FROM образ AS имя`: начинает новый этап и присваивает ему псевдоним (alias).
- `COPY --from=имя`: копирует файлы из другого этапа, а не из контекста сборки.

```
FROM golang:1.26 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN go build -o server .

FROM debian:bookworm-slim
WORKDIR /app
COPY --from=builder /app/server .
CMD ["./server"]
```

1. Первый этап (`builder`) использует полный образ Go, скачивает зависимости и компилирует бинарник.
2. Второй этап стартует с чистого минимального `debian:bookworm-slim` — в нём нет компилятора, нет исходников, нет кэша модулей.
3. `COPY --from=builder /app/server .` берёт только скомпилированный файл из первого этапа.

Финальный образ содержит только `debian:bookworm-slim` плюс один бинарник.

В одном Dockerfile может быть больше двух этапов. Псевдоним задаётся произвольно, но принято называть по роли: `builder`, `tester`, `deps`.

Путь в `--from` указывается относительно файловой системы того этапа, а не хост-машины. Если бинарник собирался в `/app/server`, именно этот путь указывается после `--from=builder`.

Если забыть псевдоним `AS builder` и написать `--from=0`, Docker будет использовать номер этапа (отсчёт с нуля). Это работает, но ломается при добавлении нового этапа в начало файла — лучше всегда использовать именованные псевдонимы.
