Любое приложение зависит не только от своего исходного кода. Вот типичный набор факторов, из-за которых одно и то же приложение ведёт себя по-разному на двух компьютерах:
- Версия языка/рантайма: Python 3.9 у вас, Python 3.12 у коллеги
- Системные библиотеки: Разные версии OpenSSL, libc
- Переменные окружения: У вас задан `DATABASE_URL`, у коллеги -- нет
- Операционная система: macOS у разработчика, Ubuntu на сервере
- Установленные пакеты: Вы поставили `numpy 1.24`, а в `requirements.txt` версия не зафиксирована

Всё это называется окружением.

До контейнеров команды использовали несколько подходов, каждый со своими недостатками:
- Документация по установке -- файл `README` на 3 страницы: "поставьте это, настройте то". Устаревает на следующий день после написания.
- Виртуальные окружения (virtualenv, venv) -- изолируют пакеты языка, но не системные зависимости и не версию ОС.
- Скрипты установки (shell-скрипты, Ansible, Chef) -- автоматизируют настройку, но привязаны к конкретной ОС и ломаются при обновлениях.
- Виртуальные машины -- решают проблему полностью, но весят гигабайты и запускаются минутами.

Контейнеризация -- это подход, при котором приложение упаковывается вместе со всем своим окружением в единый переносимый пакет, называемый контейнером (container). Контейнер содержит всё необходимое для запуска: код, рантайм, библиотеки, системные утилиты и настройки.

На практике это выглядит так. Вместо инструкции "поставь Python 3.11, потом pip install..." вы даёте коллеге один файл-описание (Dockerfile), из которого собирается контейнер.

Теперь коллега запускает одну команду, и приложение работает у него точно так же, как у вас -- независимо от того, какая ОС или какие пакеты установлены на его машине. Тот же контейнер без изменений поедет на тестовый сервер, а потом в продакшен. Фраза "у меня работает" перестаёт быть оправданием, потому что окружение больше не отличается.

По умолчанию Docker требует прав суперпользователя. Чтобы работать без `sudo`, добавьте своего пользователя в группу `docker`.
