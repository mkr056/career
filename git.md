# Локальные, централизованные и распределённые VCS

Системы контроля версий (VCS) прошли три этапа развития. Каждый следующий тип решал проблемы предыдущего.

Локальная система контроля версий (Local VCS) хранит всю историю изменений в базе данных на вашем компьютере. Она записывает разницу между версиями файлов (патчи) и по ним может воссоздать состояние файла на любой момент времени. Главная проблема -- работать может только один человек. Как только нужна командная работа, локальная VCS бесполезна. К тому же, если жёсткий диск выходит из строя, вся история теряется безвозвратно.

Централизованная система контроля версий (Centralized VCS, CVCS) решает проблему совместной работы. Все версии файлов хранятся на одном сервере, а разработчики подключаются к нему и забирают нужные файлы. Критический недостаток -- единая точка отказа (single point of failure). Если сервер недоступен, никто не может сохранять новые версии. Если диск сервера повреждён и резервных копий нет, вся история проекта потеряна навсегда.

Распределённая система контроля версий (Distributed VCS, DVCS) устраняет единую точку отказа. Каждый участник получает не просто последнюю версию файлов, а полную копию репозитория вместе со всей историей. Когда вы выполняете команду git clone, вы получаете полную копию репозитория -- именно так работает распределённая модель. После этой команды в папке project окажется вся история коммитов, все ветки -- полностью автономный репозиторий, с которым можно работать без доступа к серверу.

---

Любая система контроля версий хранит историю изменений проекта. Но как именно она это делает -- принципиальный вопрос. Существуют два подхода: хранить дельты (deltas) или хранить снимки (snapshots).

Большинство старых систем используют дельта-ориентированное хранение (delta-based version control). Идея простая: система запоминает первоначальную версию каждого файла, а потом для каждой следующей версии сохраняет только разницу -- дельту -- между текущим и предыдущим состоянием. Плюс: экономия места. Минусы: чем длиннее история, тем дольше восстанавливать конкретную версию -- нужно «проиграть» всю цепочку дельт, повреждение ранней дельты ломает всю последующую цепочку.

Git работает иначе. Каждый раз, когда вы фиксируете состояние проекта (делаете коммит, commit), Git сохраняет снимок -- полную картину всех файлов проекта в этот момент. Если файл не изменился, Git не копирует его заново, а ставит ссылку на уже сохранённую версию. Благодаря этому любой коммит -- самодостаточен. Чтобы посмотреть состояние проекта на коммите C, Git не пересчитывает цепочку изменений, а просто читает готовый снимок.

В Linux Git устанавливается через пакетный менеджер (package manager) — встроенную систему, которая скачивает программы из проверенных репозиториев вашего дистрибутива.

Префикс sudo (superuser do) запускает команду с правами администратора. Установка программ затрагивает системные каталоги, поэтому без sudo пакетный менеджер откажет в доступе.

Команда git config -- это основной инструмент для настройки поведения Git. Она умеет записывать и читать параметры конфигурации. Но у неё есть важная особенность: настройки хранятся не в одном месте, а на трёх разных уровнях конфигурации (configuration levels).

Флаг --local используется по умолчанию.

Когда Git ищет значение параметра, он проверяет все три уровня и берёт самый «узкий».

Git записывает имя автора и email в каждый коммит. Если вы не настроите эти данные, Git либо подставит случайные системные значения, либо вовсе откажется создавать коммит.

`Initialized empty Git repository in /home/user/my-project/.git/` говорит: в указанной директории создан пустой репозиторий (repository) — хранилище, в котором Git будет вести учёт всех изменений ваших файлов.

Команда git init выполняет одно конкретное действие: создаёт скрытую папку .git внутри текущей директории. Эта папка содержит служебные подкаталоги и файлы, которые нужны Git для работы: objects, refs/heads, refs/tags и набор шаблонных файлов. Без папки .git репозитория не существует.

Все существующие файлы получают статус неотслеживаемых (untracked).

При инициализации Git создаёт одну ветку (branch), на которой вы будете работать. Можно задать имя сразу при инициализации или настроить имя по умолчанию глобально — раз и навсегда.

Необязательно сначала переходить в нужную директорию. Можно передать путь прямо в команду. Git создаст папку (если её ещё нет) и инициализирует репозиторий внутри неё.

Согласно документации, git status отображает три категории путей:
* Различия между индексом (index) и последним коммитом -- то, что будет зафиксировано при git commit.
* Различия между рабочей директорией (working tree) и индексом -- изменения, которые ещё не добавлены через git add.
* Файлы, которые Git вообще не отслеживает -- неотслеживаемые файлы (untracked files).

Каждый файл в рабочей директории находится в одном из состояний:
* Untracked: Git не знает о файле, он никогда не добавлялся
* Staged: Файл добавлен в индекс командой git add, готов к коммиту
* Modified: Отслеживаемый файл изменён, но изменения не добавлены в индекс
* Unmodified: Файл совпадает с версией в последнем коммите

Состояние Unmodified в выводе git status не отображается

Команда git status -s выводит короткий формат (short format). Каждый файл занимает одну строку с двухбуквенным кодом состояния. Здесь A означает "добавлен в индекс", а ?? -- "неотслеживаемый". Буква в левой позиции описывает состояние индекса, в правой -- состояние рабочей директории. Символ M означает "изменён", D -- "удалён".

---
Когда вы работаете с Git, каждый файл в проекте в любой момент времени находится в одной из трёх зон.

Рабочая директория (working tree) — это обычная папка проекта на вашем диске. Git наблюдает за этой папкой, но изменения в ней ещё не сохранены в истории — они существуют только локально.

Область подготовки (staging area), она же индекс (index) — промежуточная зона между рабочей директорией и репозиторием. Технически это файл внутри папки .git, который хранит список изменений, подготовленных для следующего коммита.

Репозиторий (repository) — это папка .git в корне проекта. Здесь Git хранит всю историю: объекты, ссылки, метаданные. Когда вы выполняете git commit, содержимое staging area записывается в репозиторий как постоянный снимок (snapshot).

# Содержимое папки .git
Файл HEAD -- это маленький текстовый файл, который указывает на текущую активную ветку.

Каталог objects -- это база данных вашего репозитория. Здесь Git хранит всё содержимое файлов, информацию о коммитах и структуру каталогов. Каждый объект получает уникальное имя -- хеш из 40 символов (SHA-1). Как только вы сделаете первый коммит, внутри objects появятся папки с двухсимвольными именами (первые два символа хеша), а в них -- файлы с оставшимися 38 символами.

Каталог refs (от references -- ссылки) хранит указатели на конкретные коммиты. Внутри него обычно лежат подкаталоги:
* refs/heads/: Локальные ветки (main, feature и т.д.)
* refs/tags/: Теги -- именованные метки для важных коммитов
* refs/remotes/: Ссылки на ветки удалённых репозиториев

Каждая ветка -- это просто файл, внутри которого записан хеш последнего коммита этой ветки.

Связь между HEAD и refs простая: HEAD указывает на файл в refs/heads/, а тот файл содержит хеш коммита. Так Git знает, какой коммит сейчас активен.

Файл config -- это локальная конфигурация конкретного репозитория.

Помимо этих четырёх ключевых элементов, в .git есть файл index -- он появляется после первого git add и хранит содержимое области подготовки (staging area), а также каталог hooks со скриптами-хуками, которые Git может запускать автоматически при определённых событиях (например, перед коммитом).

HEAD -- это файл-указатель, который сообщает Git, на какой ветке вы сейчас находитесь.

Git всегда знает, куда записывать новый коммит, именно благодаря HEAD. При выполнении git commit Git смотрит в HEAD, находит текущую ветку, берёт из неё хеш родительского коммита и создаёт новый коммит поверх него.

Иногда HEAD может указывать не на ветку, а напрямую на конкретный коммит. Это состояние называется отсоединённый HEAD (detached HEAD). Оно возникает, когда вы переключаетесь на конкретный коммит по его хешу. В этом состоянии новые коммиты "повиснут в воздухе" -- они не привязаны ни к одной ветке и могут быть потеряны.
