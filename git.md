# Виды систем контроля версий (VCS)
Локальная система контроля версий (Local VCS) хранит историю изменений в базе данных на компьютере пользователя. Главный недостаток — отсутствие встроенного механизма совместной работы и обмена изменениями между разработчиками. Поэтому локальная VCS плохо подходит для командной разработки.

Централизованная система контроля версий (Centralized VCS, CVCS) решает проблему совместной работы. Все версии файлов хранятся в центральном репозитории на сервере, а разработчики подключаются к нему для получения и сохранения изменений. Главный недостаток — зависимость от центрального сервера. Если сервер недоступен, разработчики не могут сохранять новые версии в центральный репозиторий.

Распределённая система контроля версий (Distributed VCS, DVCS) не требует постоянной зависимости от центрального репозитория. Каждый участник получает полноценную копию репозитория вместе с его историей. С ней можно работать без доступа к серверу.

# Дельты vs снимки
Любая система контроля версий хранит историю изменений проекта. Но принцип хранения этой истории может различаться. Можно выделить два подхода: хранение дельт (deltas) и хранение снимков (snapshots).

При дельта-ориентированном хранении (delta-based version control) система хранит одну из версий файла, а для последующих версий сохраняет различия между состояниями — дельты. Чтобы получить определённую версию, системе необходимо восстановить её на основе сохранённой версии и соответствующих дельт. Плюс такого подхода — возможность экономить место за счёт хранения только различий между версиями. Минус — восстановление версии может требовать применения одной или нескольких дельт. Чем больше таких зависимостей, тем сложнее может быть восстановление. Конкретные системы могут использовать дополнительные оптимизации, например периодические полные копии.

Git концептуально использует другой подход. Каждый коммит представляет собой снимок состояния проекта в определённый момент времени. Если файл не изменился, Git не создаёт новую копию его содержимого, а повторно использует существующий объект. Благодаря этому каждый коммит однозначно описывает состояние всего проекта.

При этом коммит не содержит внутри себя все файлы проекта. Он ссылается на дерево (`tree`), которое, в свою очередь, содержит ссылки на объекты файлов (`blobs`) и другие деревья. Поэтому правильнее говорить, что коммит представляет полный снимок проекта, а не что он физически содержит полную копию всех файлов.

Важно также, что Git может использовать дельта-сжатие внутри `pack`-файлов для экономии места. Это не меняет концептуальную модель Git: на уровне истории коммиты представляют снимки состояния проекта, а не последовательность дельт, которые необходимо применять для получения каждого следующего состояния.

# Установка на Linux
В Linux Git обычно устанавливается через пакетный менеджер (package manager) — системный инструмент, который устанавливает программы из репозиториев, настроенных в вашем дистрибутиве.

Префикс `sudo` позволяет выполнить команду с повышенными привилегиями, обычно от имени суперпользователя `root`. При установке системных пакетов такие права обычно необходимы, поскольку пакетный менеджер изменяет системные каталоги и файлы.

# Конфигурация
Команда `git config` — основной инструмент для работы с поведением Git. Она позволяет записывать, изменять и читать параметры конфигурации. Важная особенность Git заключается в том, что настройки хранятся не в одном месте, а на трёх уровнях конфигурации (configuration levels).

![20261005161849](resources/20261005161849.png)

По умолчанию команда `git config` изменяет настройки локального репозитория, то есть используется уровень `--local`.

При поиске значения конкретного параметра Git учитывает настройки разных уровней конфигурации. Если один и тот же параметр задан на нескольких уровнях, более специфичный уровень переопределяет менее специфичный.

Git записывает имя автора и email в каждый коммит. Для этого используются параметры `user.name` и `user.email`. Если эти параметры не настроены, Git может попытаться определить имя и email из системных данных, но такое значение может быть некорректным. В зависимости от конфигурации Git также может потребовать явно настроить эти параметры перед созданием коммита.

# Инициализация локального Git-репозитория
`Initialized empty Git repository in /home/user/my-project/.git/` говорит: в указанной директории создан пустой Git-репозиторий (repository) — хранилище метаданных, с помощью которых Git будет отслеживать изменения файлов и хранить историю проекта.

Команда `git init` инициализирует Git-репозиторий в указанной директории. В обычном случае Git создаёт внутри неё скрытую папку `.git`. В ней находятся служебные файлы и каталоги, необходимые Git для работы, в том числе данные об объектах (`objects`) и ссылках (`refs`). Без этих метаданных каталог не является обычным Git-репозиторием.

Существующие файлы проекта при этом не добавляются в отслеживание автоматически. Файлы, которые не исключены правилами `.gitignore`, будут отображаться как `untracked` («неотслеживаемые»).

При инициализации Git создаёт начальную (unborn) ветку. Она пока не указывает ни на один коммит. После создания первого коммита эта ветка начинает указывать на него и получает историю. Имя начальной ветки можно задать непосредственно при инициализации, например `git init -b main`, либо настроить имя по умолчанию с помощью `init.defaultBranch`.

Необязательно сначала переходить в нужную директорию. Путь к ней можно передать непосредственно команде. Если указанной директории ещё нет, Git создаст её и инициализирует внутри неё репозиторий.

---

Согласно документации, git status отображает три категории путей:
* Различия между индексом (index) и последним коммитом -- то, что будет зафиксировано при git commit.
* Различия между рабочей директорией (working tree) и индексом -- изменения, которые ещё не добавлены через git add.
* Файлы, которые Git вообще не отслеживает -- неотслеживаемые файлы (untracked files).

Каждый файл в рабочей директории находится в одном из состояний:
* Untracked: Git не знает о файле, он никогда не добавлялся
* Staged: Файл добавлен в индекс командой git add, готов к коммиту
* Modified: Отслеживаемый файл изменён, но изменения не добавлены в индекс
* Commited (Unmodified): Файл совпадает с версией в последнем коммите

Состояние Unmodified в выводе git status не отображается

Команда git status -s выводит короткий формат (short format). Каждый файл занимает одну строку с двухбуквенным кодом состояния. Здесь A означает "добавлен в индекс", а ?? -- "неотслеживаемый". Буква в левой позиции описывает состояние индекса, в правой -- состояние рабочей директории. Символ M означает "изменён", D -- "удалён".

---
Когда вы работаете с Git, каждый файл в проекте в любой момент времени находится в одной из трёх зон.

Рабочая директория (working tree) — это обычная папка проекта на вашем диске. Git наблюдает за этой папкой, но изменения в ней ещё не сохранены в истории — они существуют только локально.

Область подготовки (staging area), она же индекс (index) — промежуточная зона между рабочей директорией и репозиторием. Технически это файл внутри папки .git, который хранит список изменений, подготовленных для следующего коммита.

Репозиторий (repository) — это папка .git в корне проекта. Здесь Git хранит всю историю: объекты, ссылки, метаданные. Когда вы выполняете git commit, содержимое staging area записывается в репозиторий как постоянный снимок (snapshot).

# Содержимое папки .git
Файл HEAD -- это маленький текстовый файл, который указывает на текущую активную ветку.

Каталог objects -- это база данных вашего репозитория. Здесь Git хранит всё содержимое файлов, информацию о коммитах и структуру каталогов. Каждый объект получает уникальное имя -- хеш из 40 символов (SHA-1). Как только вы сделаете первый коммит, внутри objects появятся папки с двухсимвольными именами (первые два символа хеша), а в них -- файлы с оставшимися 38 символами.

Каталог refs (от references -- ссылки) хранит указатели на конкретные коммиты. Внутри него обычно лежат подкаталоги:
* refs/heads/: Локальные ветки (main, feature и т.д.)
* refs/tags/: Теги -- именованные метки для важных коммитов
* refs/remotes/: Ссылки на ветки удалённых репозиториев

Каждая ветка -- это просто файл, внутри которого записан хеш последнего коммита этой ветки.

Связь между HEAD и refs простая: HEAD указывает на файл в refs/heads/, а тот файл содержит хеш коммита. Так Git знает, какой коммит сейчас активен.

Файл config -- это локальная конфигурация конкретного репозитория.

Помимо этих четырёх ключевых элементов, в .git есть файл index -- он появляется после первого git add и хранит содержимое области подготовки (staging area), а также каталог hooks со скриптами-хуками, которые Git может запускать автоматически при определённых событиях (например, перед коммитом).

HEAD -- это файл-указатель, который сообщает Git, на какой ветке вы сейчас находитесь.

Git всегда знает, куда записывать новый коммит, именно благодаря HEAD. При выполнении git commit Git смотрит в HEAD, находит текущую ветку, берёт из неё хеш родительского коммита и создаёт новый коммит поверх него.

Иногда HEAD может указывать не на ветку, а напрямую на конкретный коммит. Это состояние называется отсоединённый HEAD (detached HEAD). Оно возникает, когда вы переключаетесь на конкретный коммит по его хешу. В этом состоянии новые коммиты "повиснут в воздухе" -- они не привязаны ни к одной ветке и могут быть потеряны.

Если передать имя каталога, Git добавит в индекс все новые и изменённые файлы внутри него, включая вложенные подкаталоги. Точка (.) означает текущую директорию.

Флаг -A (или полная форма --all) работает похоже на точку, но с одним ключевым отличием — он всегда охватывает весь репозиторий, независимо от того, в какой папке вы находитесь.

Если нужно многострочное сообщение коммита, можно передать несколько -m подряд. Каждое значение станет отдельным абзацем. В результате первая строка станет заголовком коммита, а вторая -- телом (body), разделённые пустой строкой. Это удобный способ следовать формату «тема + описание», не заходя в редактор.

Флаг -a (сокращение от --all) говорит Git: «перед коммитом автоматически добавьте в индекс все изменённые и удалённые файлы, которые уже отслеживаются». Это экономит отдельный вызов git add для каждого файла.

Важное ограничение: -a не затрагивает новые файлы, которые Git ещё не знает (untracked). Для них по-прежнему нужен явный git add.

На практике -a и -m почти всегда используют вместе. Флаги можно объединить.

Это эквивалент двух команд:

```git
git add -u
git commit -m "Update styles for header"
```

Команда git add -u добавляет в индекс все изменённые и удалённые отслеживаемые файлы -- именно это делает флаг -a внутри git commit.

Commit-сообщение состоит из двух частей, разделённых пустой строкой:  тема и тело.

Императивное наклонение (imperative mood) -- это форма глагола-команды. Есть простой тест: подставьте тему в шаблон: *If applied, this commit will <ваша тема>*. 

Флаг --amend (от англ. "amend" — исправить, внести поправку) заменяет последний коммит новым. Git не «редактирует» старый коммит — он создаёт новый коммит на его месте, а предыдущий исчезает из истории.

Если коммит уже сделан, но сообщение неудачное, выполните: `git commit --amend -m "Fix typo in README"`. 

Допустим, вы сделали коммит, но забыли включить файл. Флаг --no-edit говорит Git: «Оставь сообщение коммита прежним, просто добавьте новые изменения из staging area».

Используйте --amend только для коммитов, которые ещё не отправлены в удалённый репозиторий (не были в git push). Если коммит уже на сервере и другие люди его получили, исправление через --amend с последующим git push --force создаст проблемы для всей команды — у коллег история разойдётся с вашей.

команда git log — выводит историю коммитов текущей ветки в обратном хронологическом порядке (от самого свежего к самому старому). Каждая запись по умолчанию использует формат medium и содержит четыре поля. Чтобы показать только последние N записей, добавьте флаг -<число>. git log -5 = git log -n 5 = git log --max-count=5. Когда коммитов больше, чем помещается на экран, Git открывает вывод в пейджере (pager) — обычно это программа less.

Флаг --oneline сокращает каждый коммит до одной строки: укороченный хеш и первая строка сообщения. Внутри это сокращение для --pretty=oneline --abbrev-commit.

Флаг --graph рисует текстовую схему ветвления слева от списка коммитов. Каждая ветка отображается отдельной линией, а точки слияния (merge) обозначаются соединениями линий. Это единственный способ увидеть структуру веток прямо в терминале, без графических программ. Символ * обозначает коммит, вертикальные линии | показывают параллельные ветки, а косые / и \ -- места ответвления и слияния. Флаг --graph автоматически включает топологическую сортировку (--topo-order), то есть коммиты одной ветки группируются вместе, а не перемешиваются по дате.

По умолчанию git log показывает историю только текущей ветки. Флаг --all добавляет в вывод коммиты из всех локальных и удалённых веток, а также тегов.

На практике эти три флага почти всегда используют вместе.

Флаг --author принимает строку-шаблон (pattern) и показывает только те коммиты, где имя или email автора совпадают с этим шаблоном. Шаблон работает как регулярное выражение, но для повседневных задач достаточно указать часть имени или email. Регистр букв учитывается. Если нужно игнорировать регистр, добавьте флаг -i. Если передать несколько --author, Git покажет коммиты, подходящие хотя бы под один из шаблонов.

Для ограничения по времени используются два флага:
* --since=<дата> (--after)
* --until=<дата> (--before)

Человекочитаемые выражения вроде "3 days ago", "1 month ago", "last Monday" тоже работают и очень удобны в ежедневной практике.

Команда git diff без аргументов сравнивает рабочую директорию и staging area. Это позволяет увидеть, что вы изменили в файлах, но ещё не добавили через git add. Важно: git diff без аргументов не видит новые неотслеживаемые файлы (untracked files). Если вы создали новый файл, но ни разу не делали для него git add, он не появится в выводе git diff. Если в проекте много изменённых файлов, а вас интересует только один, укажите путь после --. Разделитель -- нужен, чтобы Git не перепутал имя файла с именем ветки или другим аргументом. Можно перечислить несколько путей через пробел или указать целую директорию — тогда git diff покажет изменения во всех файлах внутри неё.

Команда git diff --staged показывает разницу между тем, что находится в staging area (индексе), и последним коммитом (HEAD). У этого флага есть полный синоним — --cached.

git diff HEAD сравнивает рабочую директорию с последним коммитом.

Первая строка любого блока изменений начинается с diff --git.

```git
diff --git a/app.py b/app.py
```

Здесь a/app.py — это старая версия файла (до изменений), а b/app.py — новая версия. Префиксы a/ и b/ — условные метки, а не реальные папки. Даже если файл не переименовывался, Git всё равно показывает оба имени.

После этого идут строки --- a/app.py и +++ b/app.py, которые дублируют, какой файл считается «старым», а какой — «новым».

Самая важная служебная строка — заголовок фрагмента (hunk header). Он выглядит так:

```git
@@ -3,7 +3,9 @@ def hello():
```

* -3,7: В старой версии фрагмент начинается со строки 3 и занимает 7 строк
* +3,9: В новой версии фрагмент начинается со строки 3 и занимает 9 строк
* def hello(): Ближайшая функция/класс над фрагментом (контекстная подсказка)

Знак - относится к старому файлу (a/), знак + — к новому (b/). Если в новой версии строк стало больше (9 вместо 7), значит, в этом фрагменте добавлено две строки.

Внутри каждого фрагмента каждая строка начинается с одного из трёх символов:
* Пробел — строка не менялась, показана для контекста (обычно по 3 строки сверху и снизу).
* Минус - — строка удалена из старой версии.
* Плюс + — строка добавлена в новой версии.

Git не знает, что вы «отредактировали» строку. Если вы поменяли одно слово в строке, diff покажет удаление старой строки целиком и добавление новой целиком. Пара «минус + плюс» подряд — это и есть изменённая строка. Привыкните к этому: diff работает построчно, а не посимвольно.

Когда в выводе несколько файлов, блоки diff --git ... идут один за другим. Каждый файл получает свой заголовок и свои фрагменты @@. Если в одном файле изменения разбросаны далеко друг от друга, Git покажет несколько фрагментов @@ подряд — каждый со своими номерами строк.

Часто нужно сравнить два произвольных коммита между собой. Для этого команде передают два хеша коммитов (commit hashes) через пробел или '..'. Git покажет, что нужно сделать с содержимым первого коммита, чтобы получить содержимое второго. Порядок аргументов важен: hash1 -- это «было», hash2 -- это «стало». Если поменять их местами, строки с + и - поменяются ролями. Вместо хеша можно использовать HEAD и суффикс ~n, чтобы не копировать хеши вручную:
* git diff HEAD~1 HEAD: Предпоследний коммит с последним
* git diff HEAD~3 HEAD: Коммит «три шага назад» с последним
* git diff HEAD~2 HEAD~1: Два старых коммита между собой

Если в проекте сотни файлов, а вас интересует один конкретный, добавьте путь после --. Можно перечислить несколько путей через пробел.

---

Ветка в Git — это лёгкий подвижный указатель на один из коммитов. Физически это файл размером 41 байт: 40 символов SHA-1-хеша коммита плюс перевод строки. Git хранит специальный указатель HEAD. Он показывает, на какой ветке вы сейчас работаете. HEAD указывает не напрямую на коммит, а на ветку, а уже ветка указывает на коммит.

Полезные флаги для просмотра веток:
* -a (--all): Показывает и локальные, и удалённые ветки
* -r (--remotes): Показывает только удалённые (remote-tracking) ветки
* -v (--verbose): Рядом с каждой веткой выводит хеш и сообщение последнего коммита
* --list <шаблон>: Фильтрует ветки по шаблону, например --list 'feature/\*'
* --show-current: Печатает только имя текущей ветки, без списка

По умолчанию новая ветка создаётся от HEAD, но можно указать любую стартовую точку (start point) -- хеш коммита, тег или имя другой ветки.

Хорошая практика -- использовать слеши для группировки: feature/signup, bugfix/header, hotfix/crash-on-start. Это не создаёт папки в интерфейсе Git, но многие GUI-клиенты отображают такие имена как дерево, что упрощает навигацию.

Исторически git checkout выполняла сразу две разные задачи: переключение между ветками и восстановление файлов из истории. Например, git checkout main переключает ветку, а git checkout main file.txt заменяет файл версией из ветки main. Это сбивало с толку, и в Git 2.23 функционал разделили: git switch отвечает только за переключение веток, а git restore -- только за восстановление файлов. Обе команды работают, ни одна не устарела, но git switch безопаснее для новичков -- она не даст случайно перезаписать файл.

Чаще всего ветку создают и сразу на неё переходят. Для этого не нужны две отдельные команды:
* git checkout -b feature/login
* git switch -c feature/login

Удобный приём -- дефис вместо имени ветки. Он означает "вернись туда, где я был до этого". Это аналог cd - в терминале.

Git откажется переключать ветку, если в рабочей директории есть незакоммиченные изменения в файлах, которые различаются между текущей и целевой веткой. Варианты действий: закоммитить изменения, отложить их через git stash (об этом будет отдельный урок) или добавить флаг --discard-changes (у switch) / -f (у checkout), чтобы отбросить изменения.

Git не просто копирует файлы из одной ветки в другую. Он выполняет трёхстороннее слияние (three-way merge). Для этого Git находит три точки:
* Общий предок (common ancestor): Последний коммит, который есть в обеих ветках -- место, где они разошлись
* Кончик текущей ветки (HEAD): Последний коммит в ветке, в которую вливаем (например, main)
* Кончик вливаемой ветки: Последний коммит в ветке, которую вливаем (например, feature)

Git сравнивает изменения каждой ветки относительно общего предка и автоматически объединяет их.

Допустим, в main есть три коммита (A, B, C), а от коммита B вы создали ветку feature и сделали в ней два коммита (D, E). Вы переключаетесь на main и запускаете слияние. Git находит общего предка (B), сравнивает изменения C относительно B и изменения D-E относительно B, а затем объединяет всё в новый коммит слияния (merge commit). Если обе ветки изменили одни и те же строки в одном файле, Git не сможет автоматически решить, какую версию оставить.

Когда вы выполняете git merge, Git анализирует историю двух веток и решает, как их объединить. Если истории разошлись (в каждой ветке есть коммиты, которых нет в другой), Git создаёт особый коммит — merge-коммит (merge commit). Именно он фиксирует факт слияния и отличается от обычного коммита одной важной деталью: у него два родителя. Благодаря двум родителям Git «помнит», из каких именно веток произошло слияние, и вся история остаётся прозрачной.

Команда git cat-file -p покажет внутреннюю структуру любого коммита.

Git автоматически подставляет сообщение вида Merge branch 'feature'. Вы можете изменить его, добавив флаг -m. Хорошая практика — указывать в сообщении, что именно было влито, особенно если в проекте много веток. Это упрощает чтение истории через git log.

Если текущая ветка не содержит коммитов, которых нет в вливаемой ветке, Git выполняет fast-forward — просто передвигает указатель ветки вперёд. В этом случае merge-коммит не нужен, потому что истории не расходились.

По умолчанию Git пытается выполнить fast-forward (перемотку): если текущая ветка не ушла вперёд, указатель просто сдвигается на последний коммит вливаемой ветки. При этом merge-коммит не создаётся и в истории не видно, что работа велась в отдельной ветке. Флаг --no-ff запрещает fast-forward и всегда создаёт merge-коммит, даже когда перемотка возможна. В результате в графе появится явная «петля», показывающая, что feature/login существовала как отдельная ветка. Это полезно в командных проектах, где важно сохранять информацию о том, какие задачи решались в каких ветках.

Флаг --squash собирает все изменения из вливаемой ветки и помещает их в рабочую директорию и индекс, но не создаёт коммит автоматически. Вам нужно сделать git commit вручную. Результат: вместо цепочки из пяти мелких коммитов ветки feature/login в main появится один аккуратный коммит. При этом связь с исходной веткой не сохраняется — у нового коммита будет только один родитель.

Если во время слияния возникли конфликты и вы решили, что сейчас не готовы их разрешать, флаг --abort отменяет слияние и возвращает репозиторий в состояние до вызова git merge. После этого рабочая директория и индекс вернутся к тому виду, в котором были до слияния. Важное условие: --abort надёжно работает, когда перед слияние у вас не было незакоммиченных изменений. Если они были, Git может не восстановить их полностью.

Конфликт появляется ровно тогда, когда обе ветки изменили одни и те же строки одного и того же файла. При слиянии Git находит общего предка (common ancestor) -- коммит, от которого разошлись ветки. Затем сравнивает каждую ветку с этим предком. Если обе ветки изменили одну и ту же строку относительно предка, возникает конфликт. Это называется трёхстороннее слияние (three-way merge): участвуют версия предка, версия текущей ветки и версия вливаемой ветки.

Когда Git не может автоматически объединить изменения из двух веток, он останавливает слияние и вставляет в проблемный файл специальные текстовые метки — маркеры конфликта (conflict markers). Эти маркеры показывают, какие именно строки конфликтуют и откуда пришла каждая версия. Ваша задача — прочитать их, выбрать нужный вариант и удалить маркеры вручную.

Три маркера и их роль:
* <<<<<<< HEAD: Начало конфликтного блока. Всё, что ниже до =\=\=\=\=\=\=, — версия из текущей ветки (той, в которую вы вливаете). HEAD указывает на последний коммит этой ветки.
* \=\=\=\=\=\=\=: Разделитель. Отделяет версию текущей ветки от версии вливаемой ветки.
* >>>>>>> feature: Конец конфликтного блока. Всё, что выше до \=\=\=\=\=\=\=, — версия из вливаемой ветки (в примере — feature).

Вам нужно заменить весь блок от <<<<<<< до >>>>>>> на итоговый текст. Есть три типичных решения.

Главное правило: в итоговом файле не должно остаться ни одной строки с <<<<<<<, ======= или >>>>>>>. Если хотя бы один маркер останется, файл будет содержать синтаксическую ошибку, а Git при следующей попытке коммита не предупредит об этом — он считает конфликт решённым после git add.

Команда git add здесь выполняет особую роль: она сообщает Git, что конфликт в этом файле разрешён (resolved). Git переводит файл из состояния unmerged в состояние staged.

Команда с флагом -d (сокращение от --delete) удаляет ветку только при условии, что все её коммиты уже доступны из текущей ветки (или из настроенной upstream-ветки). Другими словами, Git проверяет, что вы не потеряете работу.

Флаг -D (эквивалент --delete --force) удаляет ветку без проверки.

Обе команды принимают несколько имён через пробел. Git обработает каждую ветку по отдельности. Если одна из них не прошла проверку, остальные всё равно будут удалены (или проверены).

Если нужно убрать отслеживающую ветку (remote-tracking branch) вроде origin/feature-login, добавьте флаг -r. Это удаляет только локальную ссылку на удалённую ветку. Сама ветка на сервере не затрагивается. Обычно такие ссылки автоматически пересоздаются при следующем git fetch, если ветка ещё существует в удалённом репозитории.

Флаг -m (от английского move) переименовывает ветку вместе с её конфигурацией и журналом ссылок (reflog): `git branch -m старое_имя новое_имя`. Если вы уже находитесь на ветке, которую хотите переименовать, старое имя можно не указывать.

Обычный -m откажется работать, если ветка с новым именем уже существует. Флаг -M (заглавная) принудительно перезаписывает существующую ветку. Это аналог --move --force. Будьте осторожны: старая (сущевтсвующая) ветка будет потеряна.

Когда вы выполняете git merge, Git не всегда создаёт отдельный коммит слияния. Иногда он просто «перематывает» указатель ветки вперёд. Этот механизм называется fast-forward merge (дословно — «быстрая перемотка»), и это самый простой вид слияния в Git.

Git видит, что ветка main не продвинулась с момента ответвления, и просто перемещает указатель main на последний коммит ветки feature.

Слово Fast-forward в выводе при слиянии — прямое подтверждение, что Git не создал merge-коммит, а просто передвинул указатель main вперёд. После fast-forward merge история остаётся линейной (простая цепочка без развилок). Никаких дополнительных коммитов с сообщением вроде «Merge branch 'hotfix'» не появляется. Ветка hotfix как будто и не существовала — её коммиты просто стали частью main. Если хотите явно потребовать только fast-forward и получить ошибку при невозможности, используйте флаг --ff-only.

Когда вы выполняете git merge, Git сначала проверяет одно ключевое условие: расходились ли истории двух веток или нет. От ответа зависит, какой тип слияния произойдёт. В этом шаге разберём, что именно означает линейная история (linear history) и почему она является обязательным условием для fast-forward.

На языке Git: коммит, на который указывает текущая ветка, является прямым предком (direct ancestor) последнего коммита вливаемой ветки. Между ними нет коммитов, сделанных «в стороне» на текущей ветке.

Условие fast-forward формулируется в одно предложение: текущий коммит ветки, в которую вы вливаете, должен быть прямым предком последнего коммита ветки, которую вы вливаете.

Как мы видели ранее, при fast-forward Git просто перемещает указатель ветки вперёд, и никакого дополнительного коммита не создаётся. Это удобно, но у такого подхода есть серьёзный недостаток: из истории полностью исчезает информация о том, что работа велась в отдельной ветке.

Когда вы выполняете git clone, Git не просто копирует файлы. Он запоминает, откуда был взят репозиторий, и сохраняет эту связь в специальной настройке. Эта связь называется удалённый репозиторий (remote) и по умолчанию получает имя origin.

Remote -- это короткое имя-псевдоним для URL удалённого репозитория. Вместо того чтобы каждый раз вводить полный адрес вроде https://github.com/user/project.git, вы обращаетесь к нему по имени.

Как вы уже знаете, после git clone в проекте автоматически появляется удалённый репозиторий с именем origin. Но Git позволяет работать сразу с несколькими удалёнными репозиториями, управлять их именами и адресами. Для этого существует команда git remote.


Без аргументов git remote выводит список имён всех подключённых удалённых репозиториев. Флаг -v (сокращение от --verbose) добавляет к каждому имени URL-адреса для получения (fetch) и отправки (push) данных. Подкоманда add привязывает новый удалённый репозиторий под выбранным именем. Подкоманда rename меняет имя существующего удалённого репозитория. Все отслеживаемые ветки и настройки обновляются автоматически. Подкоманда remove (или короткий вариант rm) отвязывает удалённый репозиторий. Вместе с ним удаляются все связанные ветки удалённого отслеживания и настройки.

Полная форма команды выглядит так: `git push <remote> <branch>`.

Если такой ветки на сервере ещё нет, она будет создана автоматически. Когда вы клонируете репозиторий командой git clone, Git автоматически создаёт удалённый источник с именем origin -- это псевдоним URL-адреса, откуда был скачан проект. Имя origin -- это просто соглашение. Вы можете назвать удалённый репозиторий как угодно, но в подавляющем большинстве проектов основной remote называется именно так. Если не указать название ветки, отправится текущая, но только если для текущей ветки задана вышестоящая ветка (upstream branch).

Флаг -u (полная форма --set-upstream) при успешном пуше привязывает локальную ветку к удалённой. Эта привязка называется upstream (вышестоящая ветка). После неё Git запоминает, куда отправлять и откуда получать изменения для этой ветки.

Флаг --force (короткая форма -f) отключает проверку fast-forward и заставляет Git перезаписать удалённую ветку вашей локальной версией, даже если истории разошлись.

Флаг --force-with-lease делает то же, что --force, но с проверкой: он сравнивает текущее состояние удалённой ветки с тем, что Git видел при последнем fetch. Если кто-то успел запушить новые коммиты, команда откажется выполняться.

Git по умолчанию разрешает только быстрое перемещение (fast-forward) -- это когда ваш новый коммит является прямым потомком последнего коммита на удалённой ветке. Если кто-то (или вы сами с другого компьютера) уже добавил коммиты в удалённую ветку, ваша локальная ветка "отстаёт", и прямое перемещение невозможно.


Команда git pull скачает новые коммиты с сервера и объединит их с вашими. Если изменения затрагивают разные файлы, Git выполнит слияние автоматически. Если затронуты одни и те же строки -- возникнет конфликт слияния (merge conflict), который нужно разрешить вручную (это тема отдельного урока). Если вы хотите линейную историю без лишних merge-коммитов, используйте: `git pull --rebase origin main`. Эта команда "переставит" ваши коммиты поверх того, что уже есть на сервере. Результат -- чистая линейная цепочка коммитов. Может возникнуть соблазн использовать --force, о котором шла речь ранее. Но git push --force перезаписывает удалённую историю и уничтожает чужие коммиты.

git fetch — она скачивает все новые данные из удалённого репозитория, но не трогает ваши локальные файлы и ветки. Конкретно git fetch выполняет две вещи:
* Скачивает новые коммиты, файлы и теги из удалённого репозитория.
* Обновляет ветки удалённого отслеживания (remote-tracking branches) — например, origin/main. Это локальные копии-зеркала того, что сейчас на сервере.

Чтобы получить эти изменения и сразу применить их к своей ветке, используется команда git pull. git pull -- это команда, которая выполняет два действия подряд:
1. Запускает git fetch -- скачивает новые коммиты из удалённого репозитория в локальную копию, обновляя ссылки вроде origin/main.
2. Запускает git merge (или другую стратегию интеграции) -- сливает скачанные изменения в вашу текущую ветку.

Если вы успели сделать свои коммиты, пока коллега отправлял свои, истории веток расходятся. В этом случае git pull создаст merge-коммит (merge commit) -- специальный коммит, объединяющий две линии разработки.

Если в рабочей директории есть изменённые файлы, которые вы не добавили в коммит, git pull может отказаться работать.

Как мы видели ранее, обычный git pull загружает изменения и сливает их через merge. Если ваша локальная ветка разошлась с удалённой (у вас есть свои коммиты, а на сервере появились чужие), Git создаст merge-коммит (merge commit) — специальный коммит, который объединяет две линии разработки. Это работает, но засоряет историю техническими коммитами вида "Merge branch 'main' of ...".

Флаг --rebase меняет поведение: вместо слияния Git переставляет ваши локальные коммиты поверх того, что пришло с сервера. Результат — чистая, линейная история без лишних merge-коммитов.

По умолчанию git stash сохраняет два типа изменений: те, что уже добавлены в индекс (staged), и те, что изменены, но ещё не добавлены (modified). Неотслеживаемые файлы (untracked) -- то есть новые файлы, которые ни разу не были добавлены через git add -- по умолчанию не попадают в stash. Чтобы включить и их, используют флаг -u.

Если хотите дать понятное описание, добавьте флаг -m. stash@{0} — это всегда самая свежая запись. Чем больше число в фигурных скобках, тем старше запись. Стеш работает как стопка тарелок: последняя положенная лежит сверху. Если нужно достать не верхнюю, а конкретную запись, укажите её индекс. Важный момент: если при применении возникнут конфликты (conflicts), запись не удалится из списка автоматически. Вам нужно сначала разрешить конфликты, а потом вручную выполнить git stash drop, чтобы убрать запись. git stash apply Применяет изменения, но оставляет запись в списке.

Согласно официальной документации Git, .gitignore действует только на неотслеживаемые файлы (untracked files). Если файл уже был добавлен в репозиторий через git add и закоммичен, простое добавление его имени в .gitignore ничего не даст -- Git продолжит его отслеживать. Чтобы исправить ситуацию, нужно сначала убрать файл из индекса.

Отрицание — самый хитрый момент. Паттерн с ! возвращает файл в отслеживание, но только если его родительская директория не была исключена целиком. Порядок строк важен: отрицание должно идти после правила, которое оно отменяет. Если директория исключена целиком, Git даже не заглядывает внутрь неё, и отрицание для файлов внутри не действует. Паттерн без слэша в начале или середине работает на любом уровне вложенности. Паттерн со слэшем привязывается к конкретному расположению. Паттерн ** полезен, когда нужно указать путь с произвольной вложенностью.

В Git тег (tag) — это именованная метка, которую вы ставите на конкретный коммит. Git поддерживает два вида тегов, и они ведут себя по-разному. Лёгкий тег (lightweight tag)
Это простой указатель на коммит — ничего, кроме имени. Никакой дополнительной информации: ни автора тега, ни даты, ни описания. Чтобы создать лёгкий тег, достаточно написать имя без дополнительных флагов: `git tag v0.1`. Проверяем через git show. Аннотированный тег — это полноценный объект в базе Git. Он хранит:
* имя и email того, кто поставил тег (tagger);
* дату создания тега;
* сообщение (аннотацию) с описанием;
* контрольную сумму, которая гарантирует целостность.

Создаётся с флагом -a, а сообщение передаётся через -m. Вы не обязаны ставить тег только на последний коммит. Укажите хеш нужного коммита в конце команды.

По умолчанию git push не отправляет теги. Это частая ошибка новичков — тег создан локально, но коллеги его не видят. Чтобы отправить конкретный тег: `git push origin v1.0.0`. Чтобы отправить все теги разом используется --tags. Если нужно отправить только аннотированные теги (без лёгких), используйте --follow-tags. Локально тег удаляется так: `git tag -d v0.1`, с удалённого сервера — отдельной командой: `git push origin --delete v0.1`.

Номер версии всегда состоит из трёх чисел, разделённых точками: `v<MAJOR>.<MINOR>.<PATCH>`. 

major: Сломана обратная совместимость: старый код перестаёт работать с новой версией
minor: Добавлена новая функциональность, но старое поведение сохранено.
patch: Исправлена ошибка, ничего нового не добавлено

Важное правило: при увеличении старшей части все младшие сбрасываются в ноль.

Пока проект находится на ранней стадии разработки, принято использовать нулевую мажорную версию: v0.1.0, v0.2.0 и так далее. Это сигнал для всех: «API нестабилен, всё может измениться в любой момент». Как только вы готовы гарантировать стабильность — выпускаете v1.0.0.

Формально SemVer — это только цифры 1.2.3. Но в Git-сообществе принято добавлять букву v перед номером: v1.2.3. Это просто часть имени тега, чтобы сразу было видно — речь о версии. Оба варианта допустимы, главное — быть последовательным внутри проекта.

Pull Request -- это предложение влить изменения из одной ветки в другую. Вы не правите основной код напрямую, а создаёте отдельную ветку, вносите туда свои коммиты и затем через PR просите команду проверить и принять эти изменения. Согласно документации GitHub, Pull Request -- это базовый механизм совместной работы, который позволяет обсуждать и проверять код до того, как он попадёт в основную ветку.

Прежде чем откатывать что-либо в Git, нужно понять, где именно находятся ваши изменения. Git работает с тремя «слоями» данных, и каждая команда отмены действует на конкретный слой. Три слоя: рабочее дерево, индекс, история.

![20261006153919](resources/20261006153919.png)

До версии Git 2.23 единственным вариантом была команда git checkout с двойным дефисом: `git checkout -- style.css`. Эта команда берёт файл style.css из индекса (staging area) и перезаписывает им версию в рабочей директории. Если файл не был добавлен в индекс через git add, то индекс содержит версию из последнего коммита -- и именно она будет восстановлена. Двойной дефис -- здесь обязателен на практике. Начиная с Git 2.23 (август 2019) появилась команда git restore. Она делает ровно то же самое, но её назначение однозначно -- восстановление файлов.

![20261006154333](resources/20261006154333.png)

По умолчанию git restore без флагов восстанавливает файл в рабочем дереве (working tree) из индекса. Если добавить флаг --staged, команда восстановит содержимое в индексе из HEAD. Можно комбинировать оба флага, чтобы сбросить и индекс, и рабочую копию одновременно: `git restore --staged --worktree style.css`.

git revert создаёт новый коммит, который отменяет изменения указанного коммита. История при этом не переписывается -- старый коммит остаётся на месте, а поверх него появляется "коммит-отмена".

Это безопасный откат (safe revert): коллеги, которые уже забрали ваши коммиты через git pull, не столкнутся с конфликтами. Именно поэтому revert -- единственный правильный способ отменить коммит в публичной ветке (shared branch).
