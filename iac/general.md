# Декларативный vs императивный подход
Инфраструктура как код (Infrastructure as Code, IaC) — это подход, при котором серверы, сети, базы данных и другие ресурсы описываются в текстовых файлах и управляются теми же инструментами, что и программный код. Вместо того чтобы вручную кликать в веб-консоли облака или выполнять команды по SSH, инженер пишет файл конфигурации, и инструмент сам приводит инфраструктуру в нужное состояние.

Существуют два принципиально разных способа описать, что нужно сделать с инфраструктурой.

**Императивный подход**
Императивный подход отвечает на вопрос «как сделать?». Вы описываете последовательность шагов, которые нужно выполнить.

Пример на Bash — создание виртуальной машины в AWS через CLI:
```bash
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type t3.micro \
  --count 1 \
  --key-name my-key
```

Скрипт выполняет конкретные команды в заданном порядке. Если запустить его дважды, получите две виртуальные машины — инструмент не знает, что первая уже существует. Это главная проблема императивного подхода: отсутствие контроля состояния. Инженер сам должен следить за тем, что уже создано, и писать проверки вроде «если машина не существует, создайте».

**Декларативный подход**
Декларативный подход отвечает на вопрос «что должно быть?». Вы описываете желаемое конечное состояние, а инструмент сам решает, какие шаги нужно предпринять.

Пример на Terraform — тот же ресурс:
```text
resource "aws_instance" "web" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"
}
```

Здесь нет команд «создайте» или «запустите». Есть только описание: «должна существовать виртуальная машина с такими параметрами». Terraform сам сравнивает текущее состояние инфраструктуры с описанным и вносит только необходимые изменения. Если машина уже есть — ничего не произойдёт. Если параметр изменился — инструмент обновит ресурс.

# Приемущества IaC
Когда инфраструктура описана кодом, она приобретает три свойства, которые кардинально меняют работу команды.

**Идемпотентность**
Идемпотентность — это свойство операции давать одинаковый результат независимо от того, сколько раз её выполнить. Если система уже находится в нужном состоянии, повторный запуск ничего не сломает и не задублирует.

Пример на Terraform: если виртуальная машина уже создана, повторный `terraform apply` просто сообщит «No changes» и завершится без действий. Это критически важно для автоматизации: CI/CD-пайплайн может запускать применение конфигурации при каждом коммите, не боясь побочных эффектов.

**Версионирование**
Код инфраструктуры хранится в Git — а значит, к нему применимы все практики разработки.

**Воспроизводимость**
Воспроизводимость означает, что одна и та же конфигурация создаёт идентичную инфраструктуру в любом окружении и в любой момент времени.

Классическая проблема без IaC: staging-сервер настроен «примерно как продакшн», но с небольшими отличиями, которые никто не помнит. Например, полгода назад админ обновил библиотеку на staging, но забыл сделать это на production. Среды перестают быть одинаковыми. В результате баг воспроизводится только на продакшне.

С IaC один и тот же манифест разворачивает окружения `dev`, `staging` и `production` — разница только в параметрах (размер инстанса, количество реплик), но не в структуре. Новый разработчик может поднять полную копию продакшн-окружения одной командой:

```
terraform workspace new staging # создаёт отдельное изолированное окружение с именем staging
terraform apply -var-file=staging.tfvars # разворачивает инфраструктуру, подставляя настройки из файла staging.tfvars
```

Воспроизводимость также решает проблему «работает только у меня» на уровне инфраструктуры: если конфигурация описана кодом, среда одинакова для всех членов команды.

# GitOps
Представьте, что несколько инженеров одновременно вносят изменения в production-инфраструктуру: один правит конфигурацию сервера вручную через SSH, другой обновляет настройки через веб-интерфейс облачного провайдера, третий запускает скрипт со своего ноутбука. Через неделю никто не знает, в каком состоянии находится система и кто что менял. GitOps решает именно эту проблему.

GitOps — это операционная модель, в которой Git-репозиторий служит единственным источником истины для описания желаемого состояния инфраструктуры и приложений. Любое изменение в системе должно начинаться с коммита в репозиторий — и только так.

**Ключевые принципы**
Декларативность. Всё желаемое состояние системы описано в файлах репозитория: манифесты Kubernetes, конфигурации Terraform, Helm-чарты. Система должна соответствовать тому, что написано в Git.

Версионирование и история. Каждое изменение фиксируется коммитом с автором, временем и описанием. Откат к предыдущему состоянию — это `git revert` или переключение на нужный тег.

Автоматическое согласование (reconciliation). Специальный агент (оператор согласования) — например, ArgoCD или Flux — постоянно сравнивает реальное состояние кластера с тем, что описано в Git. Если они расходятся, агент автоматически приводит систему в соответствие с репозиторием. Этот компонент работает в режиме «тяни» (pull model): он сам забирает изменения из репозитория, а не получает команды извне.

Одобрение через Pull Request. Никто не меняет инфраструктуру напрямую. Изменение оформляется как PR (pull request), проходит ревью и автоматические проверки, и только после merge попадает в production.

**На практике**
Допустим, нужно увеличить количество реплик сервиса с 2 до 4. В GitOps-подходе инженер не заходит в кластер и не выполняет `kubectl scale`. Вместо этого он правит файл в репозитории:

```
# deployment.yaml — до изменения
spec:
  replicas: 2

# deployment.yaml — после изменения
spec:
  replicas: 4
```

Этот файл коммитится, создаётся PR, коллеги делают ревью, PR принимается. Агент GitOps замечает изменение в ветке `main` и применяет его к кластеру. Весь процесс задокументирован в истории Git.

**Почему pull, а не push**
В классическом CI/CD пайплайн толкает (push) изменения в целевую среду: скрипт деплоя запускается и выполняет команды. В GitOps оператор сам тянет (pull) желаемое состояние из Git и приводит среду к нему. Это принципиальное отличие: среда никогда не принимает команды напрямую от внешних систем, что сужает поверхность атаки и исключает «ручные» правки, которые не отражены в репозитории.

Если кто-то изменит конфигурацию сервера вручную, минуя Git, оператор согласования при следующей проверке откатит это изменение — среда всегда возвращается к тому, что написано в репозитории.

**Чем GitOps отличается от «просто хранить конфиги в Git»**

Хранить файлы в репозитории — необходимое, но недостаточное условие. GitOps требует, чтобы Git был авторитетным источником: реальная система всегда должна соответствовать репозиторию, а не наоборот. Если кто-то вручную изменил конфигурацию в кластере в обход Git, агент обнаружит расхождение, а при включённой автосинхронизации (`selfHeal` в Argo CD, обычная сверка в Flux) откатит изменение обратно. Это называется drift detection — обнаружение отклонений.

Такой подход исключает «снежинки» (snowflake servers) — серверы, которые незаметно обросли ручными правками и воспроизвести которые уже невозможно. В GitOps любой сервер можно пересоздать с нуля, просто применив содержимое репозитория.
