HCL (HashiCorp Configuration Language) — язык конфигурации, на котором пишется весь код Terraform. Он создан специально для описания инфраструктуры: читается как текст, но при этом строго структурирован. В отличие от JSON, HCL поддерживает комментарии, а в отличие от JSON и YAML — интерполяцию значений и именованные блоки.

Вся конфигурация Terraform состоит из блоков. Каждый блок имеет тип, необязательные метки и тело в фигурных скобках. Разберём пять ключевых блоков, с которыми вы будете работать постоянно.

**Блок provider**
После объявления провайдера нужно его сконфигурировать — передать регион, учётные данные и другие параметры подключения. Это делается в отдельном блоке `provider`.

Блок `provider` сообщает Terraform, с каким облаком или сервисом работать. Без него Terraform не знает, куда отправлять запросы.

```
provider "aws" {
  region = "eu-central-1"
}
```

Первая метка — имя провайдера. Оно должно совпадать с именем плагина, который Terraform скачает при инициализации.

Секреты (ключи доступа, токены) никогда не пишутся прямо в `.tf`-файл. Для AWS Terraform автоматически читает переменные окружения `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Для Yandex Cloud используется переменная `YC_TOKEN`. Это стандартная практика: конфигурация в коде, секреты — в окружении или в хранилище секретов.

Иногда нужно работать с двумя регионами AWS одновременно. Для этого используется псевдоним (`alias`):

```
provider "aws" {
  region = "eu-central-1"
}

provider "aws" {
  alias  = "us_east"
  region = "us-east-1"
}
```

В ресурсе нужный провайдер указывается явно: `provider = aws.us_east`.

После того как блоки `required_providers` и `provider` написаны, команда `terraform init` скачает нужные плагины в папку `.terraform/providers/` и зафиксирует их хеши в файле `.terraform.lock.hcl` — об этом подробнее в следующем шаге.

**Блок resource**
Ресурс — основная единица инфраструктуры в Terraform. Это конкретный объект: виртуальная машина, база данных, DNS-запись, S3-бакет.

```
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
}
```

Блок `resource` принимает две метки: тип ресурса (`aws_instance`) и локальное имя (`web`). Локальное имя используется только внутри конфигурации для ссылок между ресурсами. Тип ресурса всегда начинается с имени провайдера — это соглашение, а не случайность (обязан соответствовать схеме, которую определяет провайдер).

Идентификатор образа (AMI) `ami-0c55b159cbfafe1f0` здесь жёстко прописан для иллюстрации синтаксиса: он относится к региону `us-east-1`, а не к `eu-central-1` из блока `provider` выше — AMI привязан к региону и устаревает вместе с образом. Правильнее находить актуальный ID на момент применения через источник данных— блок `data`, который читает уже существующие данные, а не создаёт ресурс:

```
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
}
```

`most_recent` и `owners` сужают поиск до свежего официального образа Ubuntu (владелец — Canonical), а `data.aws_ami.ubuntu.id` — фактический ID для региона, заданного в `provider`.

При росте инфраструктуры один и тот же ресурс часто нужно создать в нескольких экземплярах: несколько виртуальных машин, несколько подсетей, несколько пользователей IAM. Terraform предлагает для этого мета-аргументы — `count` и `for_each`.

Счётчик (`count`) задаёт число копий ресурса, а обратиться к номеру текущей копии внутри блока позволяет `count.index`.

```
resource "aws_instance" "worker" {
  count         = 3
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  tags = {
    Name = "worker-${count.index}"
  }
}
```

Terraform создаёт ресурсы с адресами `aws_instance.worker[0]`, `aws_instance.worker[1]`, `aws_instance.worker[2]`. Слабое место `count` — привязка к позиции в списке, а не к содержимому. При удалении элемента из середины списка: если убрать `worker[1]`, элемент, ранее стоявший под индексом 2, сдвигается на индекс 1. Terraform интерпретирует это как изменение существующего ресурса, а не как удаление одного элемента, и может уничтожить и пересоздать сразу несколько соседних ресурсов вместо одного. Для ресурсов без состояния это просто неудобство, а для ресурсов с состоянием — дисков, баз данных — риск потери данных. Подходит для набора полностью одинаковых копий, где порядок не важен и удаление всегда происходит с конца списка.

Поэлементный перебор (`for_each`) принимает карту (map) или множество (set) строк и создаёт по одному ресурсу на каждый ключ. Адрес ресурса строится по ключу, а не по числовой позиции, поэтому порядок элементов и удаление соседних значений на него не влияют.

```
locals {
  workers = {
    "eu" = "t3.micro"
    "us" = "t3.small"
  }
}

resource "aws_instance" "worker" {
  for_each      = local.workers
  ami           = data.aws_ami.ubuntu.id
  instance_type = each.value
  tags = {
    Name = "worker-${each.key}"
  }
}
```

`each.key` и `each.value` ссылаются на ключ и значение текущей итерации. Удаление ключа `"eu"` из карты приведёт к уничтожению только `aws_instance.worker["eu"]`, остальные ресурсы адрес не меняют и не пересоздаются.

Локальные значения (`locals`) хранят промежуточные вычисления и переиспользуемые константы, чтобы не дублировать выражения по всей конфигурации. В примере выше `local.workers` задаёт карту окружений в одном месте: чтобы добавить новое окружение, достаточно добавить одну строку в карту — `for_each` создаст для неё ресурс автоматически, без правки остального кода.

Ещё один способ избежать жёстко заданных значений — источник данных (data source) `data "aws_ami"`, который на этапе `plan` запрашивает у облачного провайдера актуальный образ вместо захардкоженного ID:

```
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }
}
```

Захардкоженный ID образа привязан к конкретному региону и со временем устаревает — провайдер может прекратить его поддержку. Источник данных `aws_ami` всегда возвращает актуальный на момент запуска `plan` образ, соответствующий заданным фильтрам, и работает в любом регионе без изменения кода.

Источники данных вместо жёстко заданных значений. Идентификаторы вроде AMI (Amazon Machine Image, образ виртуальной машины) меняются с выходом новых версий. Хранить в коде конкретный идентификатор образа — плохая практика: рано или поздно значение устареет. Источник данных (data source) запрашивает актуальное значение у провайдера на этапе построения плана, а не хранит его в коде.

```
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-*-amd64-server-*"]
  }
}
```

`most_recent = true` указывает Terraform выбрать самый свежий образ среди удовлетворяющих фильтру, а его идентификатор доступен через `data.aws_ami.ubuntu.id`. Обратите внимание на суффикс `amd64` в шаблоне имени: без него под фильтр попали бы и образы для архитектуры ARM, несовместимые с типами инстансов `t3`. Конфигурация перестаёт зависеть от конкретного значения и не требует ручного обновления при выходе нового образа.

**Блок variable**
Variable позволяет параметризовать конфигурацию — вынести значения, которые меняются между окружениями (dev, staging, prod), в отдельные определения.

```
variable "instance_type" {
  type        = string
  default     = "t3.micro"
  description = "Тип инстанса EC2"
}
```

Чтобы использовать переменную в ресурсе, обращаются через префикс `var.`. ID образа по-прежнему разумно брать из `data`, а не задавать напрямую:

```
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type
}
```

Если `default` не задан, Terraform возьмёт значение из файла `terraform.tfvars` или флага `-var`, а если значение нигде не найдено — запросит его интерактивно при запуске.

**Блок output**
Output — способ получить значение из Terraform после применения конфигурации. Это удобно, когда нужно узнать IP-адрес созданной машины или ARN ресурса, не заходя в консоль облака.

```
output "instance_public_ip" {
  value       = aws_instance.web.public_ip
  description = "Публичный IP созданного инстанса"
}
```

Обратите внимание на синтаксис ссылки: `тип_ресурса.локальное_имя.атрибут`. Это стандартный способ обращаться к атрибутам других ресурсов в HCL. После выполнения `terraform apply` Terraform выведет значение `instance_public_ip` прямо в терминал.

Грабли, на которые наступают первыми: путать имя блока с обращением к нему. Блок `variable` объявляется как `variable "name" {}`, а используется как `var.name`; блок `data` — аналогично, через префикс `data.тип.имя`. Блок `output`, в отличие от них, сам ни к чему не обращается через собственный префикс.
