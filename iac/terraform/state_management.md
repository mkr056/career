Когда Terraform создаёт, изменяет или удаляет ресурсы в облаке, ему нужно где-то хранить информацию о том, что уже существует. Для этого служит файл состояния (state file) — `terraform.tfstate`. Без него Terraform не может сопоставить описание в коде с реальными объектами в инфраструктуре.

Файл состояния — это JSON-документ, который Terraform генерирует и обновляет автоматически. В нём хранятся:
- идентификаторы реальных ресурсов (например, `i-0a1b2c3d` для EC2-инстанса в AWS);
- значения всех атрибутов ресурса на момент последнего `apply`;
- метаданные зависимостей между ресурсами;
- версия схемы провайдера.

Каждый раз, когда вы выполняете `terraform plan` или `terraform apply`, Terraform делает три шага:

1. Читает текущий `terraform.tfstate` — это «что было создано».
2. Запрашивает реальное состояние ресурсов через API провайдера — это «что есть сейчас».
3. Сравнивает оба состояния с кодом в `.tf`-файлах — это «что должно быть».

Расхождение между этими тремя источниками и определяет план изменений. Если кто-то вручную удалил ресурс в консоли AWS, но state об этом не знает, Terraform при следующем `plan` обнаружит расхождение и предложит пересоздать ресурс.

По умолчанию `terraform.tfstate` появляется в той же директории, где вы запускаете команды Terraform. Рядом с ним при каждом `apply` создаётся резервная копия `terraform.tfstate.backup` — на случай если текущий файл окажется повреждён.

Важно: `terraform.tfstate` может содержать чувствительные данные — пароли, ключи доступа, строки подключения к базам данных. Именно поэтому его нельзя коммитить в публичный репозиторий. Стандартная практика — добавить его в `.gitignore`:

```
# .gitignore
*.tfstate
*.tfstate.backup
```

Локальное хранение state удобно для экспериментов одного разработчика, но в командной работе сразу возникают проблемы: два инженера не могут одновременно запускать `apply`, и у каждого будет своя копия файла. Решение — удалённый бэкенд: место за пределами вашей машины, куда Terraform записывает и читает файл состояния.

#  Удаленный бекенд
Удалённый бэкенд решает три задачи сразу:

- Общий доступ — все члены команды работают с одним и тем же state.
- Блокировка (state locking) — пока один инженер выполняет `apply`, другой не может запустить свой, и state не повреждается.
- Безопасность — state не лежит в Git-репозитории, где могут оказаться пароли и токены.

Варианты: S3 (AWS): современный вариант с native locking, Легаси-вариант: DynamoDB, GCS (Google Cloud Storage), HCP Terraform (бывший Terraform Cloud).

Типовая ошибка при первой настройке — указать несуществующий бакет: Terraform сообщит об этом на этапе `init`, а не `apply`, поэтому инфраструктуру для state принято создавать отдельно — вручную или отдельным корневым модулем с локальным бэкендом.

# Управление ресурсами в state
Когда инфраструктура уже существует — создана вручную в консоли или другим инструментом — Terraform о ней ничего не знает. Если описать такой ресурс в `.tf`-файле и выполнить `apply`, Terraform попытается создать дубликат: для ресурсов с глобально уникальными именами (например, S3-бакетов) провайдер вернёт ошибку о занятом имени, а ресурсы без таких ограничений (например, EC2-инстансы) будут молча созданы второй раз. Для таких ситуаций существуют команда `terraform import` и одноимённый декларативный блок `import`, а для переноса ресурсов внутри state — команда `terraform state mv` и блок `moved`.

**terraform import: добавление существующего ресурса в state**
`terraform import` — команда, которая связывает уже существующий облачный ресурс с блоком конфигурации в вашем `.tf`-файле, записывая его в `terraform.tfstate`.

Порядок работы такой:

1. Сначала вы вручную описываете ресурс в конфигурации.
2. Затем выполняете `import`, передавая адрес ресурса в state и идентификатор реального объекта в облаке.

```
# Синтаксис
terraform import <адрес_в_state> <идентификатор_в_облаке>

# Пример: импорт существующего S3-бакета
terraform import aws_s3_bucket.my_bucket my-existing-bucket-name

# Пример: импорт EC2-инстанса
terraform import aws_instance.web i-0abcd1234ef567890
```

После выполнения команды Terraform записывает текущее состояние ресурса в state-файл. Теперь `terraform plan` покажет расхождения между реальным ресурсом и вашей конфигурацией — и вы сможете привести `.tf`-файл в соответствие.

Здесь регулярно ошибаются: запустить `import` без предварительного описания ресурса в конфигурации. Terraform выдаст ошибку `resource address ... does not exist in the configuration` (файл не создастся сам).

**terraform state mv: перемещение ресурсов внутри state**
`terraform state mv` перемещает запись о ресурсе внутри state-файла без каких-либо изменений в реальной инфраструктуре. Это нужно в двух типичных ситуациях:

- Переименование ресурса в конфигурации: если вы переименовали `aws_instance.old_name` в `aws_instance.new_name`, Terraform без `state mv` удалит старый и создаст новый инстанс.
- Перенос ресурса в модуль: когда вы рефакторите конфигурацию и оборачиваете ресурсы в модуль.

```
# Переименование ресурса
terraform state mv aws_instance.old_name aws_instance.new_name

# Перенос ресурса в модуль
terraform state mv aws_s3_bucket.logs module.storage.aws_s3_bucket.logs
```

После выполнения `state mv` запустите `terraform plan` — план должен показать `No changes`, если конфигурация совпадает с новым адресом в state.

**Декларативный рефакторинг: блоки moved и import**

Начиная с Terraform 1.1 доступен блок `moved`, а начиная с Terraform 1.5 — блок `import`. Это декларативные альтернативы командам `state mv` и `import`: вместо разовой ручной команды в терминале вы описываете намерение прямо в коде конфигурации, оно попадает в pull request, проходит код-ревью и применяется автоматически при следующем `terraform plan` и `apply` — как и любое другое изменение инфраструктуры.

Переименование и перенос в модуль через блок `moved` выглядят так:

```
# Переименование ресурса
moved {
  from = aws_instance.old_name
  to   = aws_instance.new_name
}

# Перенос ресурса в модуль
moved {
  from = aws_s3_bucket.logs
  to   = module.storage.aws_s3_bucket.logs
}
```

При запуске `terraform plan` Terraform сам находит запись `from` в state, переносит её на адрес `to` и показывает в плане пометку «moved», а не «destroy/create». Блок можно оставить в конфигурации на постоянной основе — он безопасен для повторного применения и просто ничего не делает, если ресурс уже перенесён.

Импорт существующего ресурса через блок `import` выглядит так:

```
import {
  to = aws_instance.web
  id = "i-0abcd1234ef567890"
}

resource "aws_instance" "web" {
  # конфигурация ресурса
}
```

Ключевое преимущество блока `import` — команда `terraform plan -generate-config-out=generated.tf`: Terraform подключается к облачному провайдеру, считывает фактические атрибуты ресурса и сам генерирует для него черновик `resource`-блока. Вам не нужно вручную угадывать все аргументы существующего ресурса — достаточно проверить и доработать сгенерированный файл. Генерация работает только для блока `import`, у которого в конфигурации ещё нет блока `resource`; в примере выше блок `resource` уже написан, поэтому для него код не генерируется.

Команды `terraform import` и `terraform state mv` никуда не делись и остаются удобными для разовой ручной правки state прямо в терминале. Но для командной работы декларативные блоки предпочтительнее: они версионируются в Git вместе с остальной конфигурацией, проходят тот же процесс проверки, что и любой другой pull request, и не требуют, чтобы кто-то помнил и вручную выполнил нужную команду перед следующим `apply`.

**Дополнительные команды для работы со state**
`terraform state list`: Показывает все ресурсы в state
`terraform state show <адрес>`: Выводит атрибуты конкретного ресурса
`terraform state rm <адрес>`: Удаляет ресурс из state (не из облака)

`terraform state rm` полезен, когда нужно «забыть» ресурс — например, если вы хотите исключить его из управления Terraform, не удаляя физически.

Все операции со state при использовании удалённого хранилища состояния (remote backend, например S3 или GCS) выполняются над удалённым файлом автоматически — локальный `terraform.tfstate` при этом не затрагивается.
