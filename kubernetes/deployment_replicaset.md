# ReplicaSet
Представьте — что-то пошло не так c pod'ом. OOM-killer убил процесс. Pod перешёл в Failed. И всё. Pod сам себя не воскрешает. K8s не перезапустит этот конкретный Pod — он просто оставит его в Failed. Сервис лежит. Чтобы Pod восстанавливался — нужна обёртка над ним.

ReplicaSet — это объект который гарантирует: «должно быть N таких Pod'ов в любое время».

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
```

Что тут:  
- `replicas: 3` — должно быть 3 Pod'а.  
- `selector` — как ReplicaSet находит свои Pod'ы (по labels).  
- `template` — шаблон для создания новых Pod'ов.

Что делает ReplicaSet:  
1. Создаёт 3 Pod'а по шаблону.  
2. Постоянно проверяет: «сколько Pod'ов с label `app: web` существует?».  
3. Если 3 — ничего не делает.  
4. Если 2 (один упал) — создаёт ещё один.  
5. Если 4 (вы создали лишний руками) — удаляет один.

Это и есть self-healing. Pod упал → ReplicaSet видит «2 вместо 3» → создаёт новый Pod → опять 3. Нода упала → все Pod'ы с неё пропали → ReplicaSet видит нехватку → новые Pod'ы создаются на других нодах.

Есть проблема: что если вы захотите обновить образ на новую версию? У ReplicaSet нет встроенного механизма для постепенного обновления. Придётся вручную. Поэтому в реальности используется Deployment — это «ReplicaSet + механизм обновлений».

# Deployment
Deployment — это объект которым на самом деле пользуются в 99% случаев. Под капотом он создаёт ReplicaSet'ы, но даёт дополнительную фичу — rolling update: обновление образа без даунтайма.

Манифест Deployment:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
```

Похоже на ReplicaSet, да? Так и есть — Deployment обёртка над ReplicaSet. Когда вы применяете Deployment:
1. Создаётся ReplicaSet с указанными настройками.
2. ReplicaSet поднимает 3 Pod'а.

Меняете `image: nginx:1.25` → `image: nginx:1.26` и делаете `kubectl apply`:
1. Deployment создаёт новый ReplicaSet с новым образом (старый ReplicaSet ещё работает с 3 Pod'ами).
2. Новый ReplicaSet поднимает 1 Pod с новой версией.
3. Когда новый Pod готов (прошёл readiness) — старый ReplicaSet гасит один свой Pod.
4. Повторяет: создал новый → погасил старый.
5. В конце старый ReplicaSet с 0 Pod'ами, новый с 3 Pod'ами.

Сменить образ в Deployment'е и запустить обновление можно используя: `kubectl set image <РЕСУРС>/<ИМЯ_РЕСУРСА> <ИМЯ_КОНТЕЙНЕРА>=<НОВЫЙ_ОБРАЗ>`.

Это и есть rolling update. Пользователи ничего не заметили — сервис не падал.

Что-то пошло не так с новой версией? Откат одной командой: `kubectl rollout undo deployment/my-web`.  Deployment вернётся к предыдущему ReplicaSet'у. Снова rolling update, но в обратную сторону.

К8s хранит историю ReplicaSet'ов (по умолчанию 10 последних). Можно откатиться на любую старую версию.

```
Deployment
   └─ ReplicaSet (текущая версия)
       └─ Pod 1
       └─ Pod 2
       └─ Pod 3
   └─ ReplicaSet (старая версия, 0 Pod'ов, хранится для rollback)
```

У Deployment есть два режима обновления.

**RollingUpdate (по умолчанию)**
```yaml
spec:
  strategy:
    type: RollingUpdate
```

То что мы разбирали — постепенно гасим старые Pod'ы, поднимаем новые. Сервис не падает во время обновления.

В любой момент во время обновления могут одновременно работать Pod'ы старой и новой версии. Это важно — ваше приложение должно быть готово к этому. Например, если у вас миграции БД, новый код должен работать со старой схемой (пока миграция не применена). Всегда использовать для production. Это правильный подход.

Когда Deployment делает RollingUpdate, у него два рычага: `maxSurge` и `maxUnavailable`.

`maxSurge` — сколько лишних Pod'ов можно поднять. Сколько Pod'ов могут существовать сверх желаемого числа во время обновления.

`maxSurge: 1` при `replicas: 3` означает: в момент обновления может быть до 4 Pod'ов (3 + 1 новый).

`maxSurge: 50%` = 50% от replicas. При replicas: 4 → можно поднять 2 новых одновременно (всего 6).

Чем больше maxSurge, тем быстрее обновление (поднимаются несколько новых Pod'ов параллельно). Но требует больше ресурсов на нодах в момент обновления.

`maxUnavailable` — сколько Pod'ов может быть недоступно. Сколько Pod'ов могут быть не готовы во время обновления.

`maxUnavailable: 0` при `replicas: 3` означает: в любой момент должно быть готово все 3 Pod'а. K8s не погасит старый Pod пока новый не стал ready. `maxUnavailable: 1` означает: допустимо иметь 2 готовых из 3 (один обновляется). Чем меньше maxUnavailable, тем безопаснее, но медленнее обновление.

Типичные настройки:
Безопасная (для критичного prod)
```yaml
strategy:
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```
Гарантия: всегда работают все реплики. Лишний Pod ради безопасности.

Быстрая (для dev/staging):
```yaml
strategy:
  rollingUpdate:
    maxSurge: 50%
    maxUnavailable: 25%
```
Обновляется быстро, можно немного потерять в готовности.

Дефолтная:
```yaml
strategy:
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 25%
```
K8s ставит это если не указано явно. Подходит для большинства случаев.

**Recreate**
```yaml
spec:
  strategy:
    type: Recreate
```

Сначала гасит все старые Pod'ы, потом поднимает новые. Между этим — даунтайм.

Использовать Recreate — только если точно знаете что не можете иметь две версии одновременно. И тогда лучше планировать обновления на ночь когда нагрузка низкая.
