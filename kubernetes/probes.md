Kubernetes сам по себе не знает, всё ли в порядке с приложением: процесс может быть запущен, но давно завис или ещё не готов принимать запросы. Единственный способ выяснить его состояние — периодически выполнять проверки. Для этого служат пробы (probes): livenessProbe, readinessProbe и startupProbe. Каждая отвечает на свой вопрос.

# livenessProbe
livenessProbe отвечает на вопрос «жив ли процесс внутри контейнера, не завис ли он». Если проверка проваливается подряд заданное число раз, kubelet завершает и перезапускает контейнер. В эту пробу стоит закладывать только проверку собственного состояния процесса, например ответ веб-сервера на простой запрос. Проверять здесь доступность внешней базы данных нельзя: при временной недоступности БД проба начнёт падать сразу у всех подов, kubelet начнёт перезапускать их контейнеры, а после рестарта зависимость всё ещё недоступна — возникает каскад рестартов, который лишь усугубляет инцидент.

# readinessProbe
readinessProbe отвечает на вопрос «готов ли под принимать входящий трафик прямо сейчас». Провал этой проверки не ведёт к перезапуску: под просто исключается из списка `Endpoints` / `EndpointSlices` у Service и перестаёт использоваться для обычной маршрутизации трафика, пока проверка снова не станет успешной. Именно здесь уместно проверять зависимости — подключение к базе, доступность кеша, прогрев данных при старте. Если readinessProbe не задана вовсе, кластер считает под готовым сразу после запуска контейнера, и трафик пойдёт в него раньше, чем приложение реально сможет его обработать: часть запросов завершится ошибками.

# startupProbe
startupProbe нужна приложениям с медленным стартом. Пока она не подтвердит успешный запуск, liveness и readiness не выполняются вовсе, и долгая инициализация не приводит к преждевременному рестарту по liveness.

# Способы проверки
- `httpGet` — HTTP-запрос по указанному пути и порту, успехом считается код ответа от 200 до 399.
- `tcpSocket` — попытка открыть TCP-соединение с портом, подходит, если у сервиса нет HTTP-эндпоинта.
- `exec` — выполнение команды внутри контейнера, успех определяется по коду завершения, ноль означает успех.

# Ключевые параметры
- `initialDelaySeconds` — задержка перед первой проверкой после старта контейнера.
- `periodSeconds` — интервал между последовательными проверками.
- `failureThreshold` — сколько подряд неудачных проверок нужно, чтобы считать пробу проваленной.
- `timeoutSeconds` — сколько времени кластер ждёт ответа на одну проверку, прежде чем засчитать её неудачной.

# Пример: Deployment с обеими пробами
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: web-app
          image: myregistry/web-app:1.4.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
```

Обратите внимание на разные пути в примере: `/ready` проверяет готовность вместе с зависимостями, а `/healthz` проверяет только сам процесс, без обращения к базе или внешним сервисам. Такое разделение эндпоинтов на стороне приложения — обязательное условие того, чтобы обе пробы выполняли свою задачу, а не дублировали друг друга.
