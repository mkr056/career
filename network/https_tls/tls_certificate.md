TLS-рукопожатие дало нам конфиденциальность и целостность. Но осталась третья гарантия — аутентичность: как браузер убеждается, что на том конце `shop.example.com`, а не подставной сервер злоумышленника? Ответ — TLS-сертификат.

Сертификат — это не «ключ шифрования». Это, по сути, цифровой паспорт: документ, который связывает доменное имя с публичным ключом и заверен подписью того, кому мы доверяем. Внутри сертификата лежат:
- Subject / CN: на какое имя выписан (`CN = shop.example.com`)
- SAN: список всех доменов, для которых он валиден (`shop.example.com`, `www.shop.example.com`)
- Issuer: кто выдал и подписал (удостоверяющий центр)
- notBefore / notAfter: срок действия — с какой по какую дату
- Public Key: публичный ключ сервера
- Serial: серийный номер, уникальный у выдавшего CA

Ключевая идея: сам по себе сертификат — просто текст. Любой может напечатать бумагу «я — shop.example.com». Ценность ему придаёт подпись удостоверяющего центра. Поэтому когда сервер в рукопожатии присылает сертификат, браузер проверяет две вещи: имя (совпадает ли домен из адресной строки с Subject/SAN) и подпись (заверил ли его тот, кому мы доверяем).

Удостоверяющий центр (CA, Certificate Authority) — организация, чьей подписи браузеры и ОС доверяют «из коробки». В вашей системе есть хранилище корневых сертификатов (root store) — заранее вшитый список доверенных CA (DigiCert, Let's Encrypt / ISRG, GlobalSign и др.). Всё доверие в вебе отталкивается от этого списка.

Но корневой CA не подписывает сертификаты сайтов напрямую — его приватный ключ слишком ценен, чтобы использовать его каждый день. Вместо этого выстраивается цепочка доверия:

```
Root CA  (в хранилище системы, доверенный)
   │ подписывает
   ▼
Intermediate CA  (промежуточный, рабочая лошадка)
   │ подписывает
   ▼
Сертификат сайта  (leaf, shop.example.com)
```

Браузер проверяет цепочку снизу вверх: сертификат сайта подписан промежуточным → промежуточный подписан корневым → корневой лежит в доверенном хранилище. Дошли до доверенного корня — цепочка собралась, соединению верим.

Отсюда важнейшая практическая деталь: сервер обязан отдавать в рукопожатии не только свой сертификат, но и промежуточные. Если админ забыл настроить промежуточный сертификат, браузер получит только leaf, не сможет достроить путь до корня — и выдаст ошибку «unable to get local issuer certificate». Самый коварный случай: в Chrome сайт работает (браузер докачал промежуточный из кэша), а `curl` на сервере — падает. Причина одна: неполная цепочка.

Проверка имени. Исторически домен писали в поле CN (Common Name) внутри Subject. Сегодня это устарело: современные браузеры проверяют имя только по SAN (Subject Alternative Name) — списку доменов в сертификате. Если в SAN нет домена из адресной строки, будет ошибка совпадения имени, даже когда CN «на глаз» правильный. CN оставляют для читаемости, но решает SAN.

Самоподписанный сертификат — сервер сам себе CA: Issuer совпадает с Subject. Технически шифрование работает, но такому паспорту никто не доверяет по умолчанию — отсюда предупреждение браузера. Годится для локальной разработки, не для прода.

Let's Encrypt — бесплатный CA, выдавший добрую половину сертификатов в интернете. Его особенность — короткий срок в 90 дней (норма, не баг): предполагается автопродление. Если автопродление упало, сертификат просто протухнет — частая причина внезапной поломки.

Отдельный случай, который не ловится по тексту про сертификат: страница загрузилась по HTTPS, но тянет картинку/скрипт по `http://`. Браузер блокирует такой «смешанный контент» из соображений безопасности. Это не про сертификат сервера — лечится заменой `http://` на `https://` в ссылках ресурса. Держи в голове как четвёртый, отдельный симптом.
